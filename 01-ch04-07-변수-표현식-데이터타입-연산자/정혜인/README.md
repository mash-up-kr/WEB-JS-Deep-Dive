<summary>메모리 주소 ↔ React useEffect 무한 루프</summary>

**전제 1.** 객체 리터럴은 평가될 때마다 **새 객체를 새 주소에** 생성한다. 구조가 같아도 주소가 다르다.

```javascript
({ a: 1 }) === ({ a: 1 })   // false
[] === []                   // false
(() => {}) === (() => {})   // false
```

**전제 2.** `useEffect`의 의존성 배열은 매 렌더마다 `Object.is`로 **얕게** 비교한다. 깊은 비교를 하지 않는다. 따라서 객체·배열·함수는 **주소만** 비교된다.

```javascript
function List() {
  const [data, setData] = useState(null);
  const options = { page: 1 }; // 매 렌더마다 새 주소

  useEffect(() => {
    fetchData(options).then(setData); // setData가 렌더를 유발
  }, [options]); // 주소가 매번 달라 항상 "변경됨"
}
```

### 무한 루프의 조건 2가지

"새 참조가 생기면 무한 루프"는 반쯤만 맞는 설명. 조건이 둘 다 있어야 한다.

1. 의존성의 참조가 매 렌더마다 바뀜 → 이펙트가 매 렌더마다 재실행
2. 그 이펙트가 상태를 변경함 → 렌더를 유발

1번만 있으면 무한 루프가 아니라 그냥 **불필요한 재실행(낭비)** 이다. 2번이 붙어서 사이클이 닫힐 때 무한 루프가 된다.

```plaintext
렌더 → 새 객체 생성 → 의존성 변경 감지 → 이펙트 실행 → setState → 렌더 → ...
                                                        ↑
                                            이 화살표가 없으면 무한 루프 아님
```

### 해결책과 각각이 바꾸는 것

| 방법               | 무엇을 하는가                                | 언제                               |
| ------------------ | -------------------------------------------- | ---------------------------------- |
| 원시값으로 쪼개기  | 비교 대상을 참조에서 값으로 바꿈             | 필드가 적을 때. **1순위로 고려**   |
| `useMemo`          | 객체 참조를 렌더 간에 유지                   | 객체를 통째로 넘겨야 할 때         |
| `useCallback`      | 함수 참조를 유지                             | 함수를 의존성이나 prop으로 넘길 때 |
| 함수형 업데이트    | 의존성 자체를 **제거**                       | 이전 상태만 필요할 때. 가장 깔끔   |
| `useRef`           | 값은 들고 있지만 렌더·비교에 참여시키지 않음 | 변경돼도 재실행이 불필요할 때      |
| 모듈 스코프로 이동 | 애초에 렌더 중에 생성하지 않음               | 상수 객체일 때. 자주 놓치는 정답   |

원시값으로 쪼개는 걸 1순위로 두는 이유: `useMemo`는 근본 해결이 아니라 **참조 관리 책임을 개발자에게 하나 더 얹는 것**이다. 의존성이 원시값이면 애초에 관리할 게 없다.

### 💭 고민 포인트

**React는 왜 깊은 비교를 하지 않는가?**

- 비용이 예측 불가능. 참조 비교는 O(1), 깊은 비교는 O(n)이고 n을 React가 알 수 없다
- 함수는 원리적으로 비교 불가능. "같은 일을 하는 함수인가"는 판정할 수 없다
- 순환 참조 시 무한 순회 위험

<summary>var / let / const 의 생명 주기</summary>

### 핵심 원칙 하나

> **변수의 생명 주기는 키워드가 정하는 게 아니다. 그 변수가 등록된 렉시컬 환경(스코프)의 생명 주기와 같다.**

함수의 지역 변수는 실행 컨텍스트가 생성될 때 태어나고 컨텍스트가 팝될 때 죽는다. 키워드는 여기에 세 가지 변수를 더할 뿐이다. (본격적인 내용은 14.1절)

### 생명 주기 5단계

`선언(등록) → TDZ → 초기화 → 사용/재할당 → 소멸`

|                      | `var`                   | `let`                          | `const`                |
| -------------------- | ----------------------- | ------------------------------ | ---------------------- |
| **선언(등록)**       | 평가 단계               | 평가 단계                      | 평가 단계              |
| **TDZ 구간**         | 없음 (길이 0)           | 선언문 도달까지                | 선언문 도달까지        |
| **초기화**           | 평가 단계에 `undefined` | 런타임, 선언문 도달 시         | 런타임, 선언문 도달 시 |
| **초기화 생략**      | 가능                    | 가능 (`undefined`)             | **불가** (SyntaxError) |
| **소멸 기준 스코프** | 함수 레벨               | 블록 레벨                      | 블록 레벨              |
| **전역일 때 소속**   | `window`의 프로퍼티     | 보이지 않는 선언적 환경 레코드 | 동일                   |

**(a) TDZ는 버그가 아니라 생명 주기의 한 단계다.** `let`도 호이스팅은 된다(등록은 평가 단계에 됨). 초기화만 뒤로 미뤄져서 그 사이 접근하면 `ReferenceError`. **`var`는 TDZ 길이가 0인 특수 케이스**로 보는 게 정확한 모델. "let은 호이스팅 안 된다"는 흔한 오답.

**(b) `const`는 선언과 초기화가 분리될 수 없다.** 재할당 금지라서 초기화를 미루면 영원히 값을 못 넣게 되니까. (15.3.1절)

**(c) 전역에서의 소속이 생명 주기를 바꾼다.** 전역 `var`는 `window`의 프로퍼티가 되고 `window`는 앱이 끝날 때까지 산다. 즉 **전역 `var`는 사실상 절대 GC되지 않는다** — 14.2절 전역 변수 문제점의 핵심. 전역 `let` · `const`는 `window`에 붙지 않아 `window.x`로 접근 불가.

### 생명 주기 차이를 눈으로 보는 예제 — 면접 단골

```javascript
for (var i = 0; i < 3; i++) setTimeout(() => console.log(i));
// 3, 3, 3

for (let i = 0; i < 3; i++) setTimeout(() => console.log(i));
// 0, 1, 2
```

- `var`: 변수가 **딱 하나**. 스코프에 하나 생기고 루프 전체를 산다. 콜백 3개가 같은 변수를 가리키고 실행 시점엔 이미 3
- `let`: 명세가 **반복마다 새로운 바인딩**을 만들도록 정의했다. 변수가 3개 생기고 각각 별도의 생명 주기를 가진다

즉 `let`이 정답을 주는 이유는 "블록 스코프라서"가 아니라 **"반복마다 변수의 생명 주기가 새로 시작되어서"** 다.

### 💭 고민 포인트

**클로저는 변수의 생명 주기를 연장한다 — 언제 누수가 되는가?**

내부 함수가 외부 스코프의 변수를 참조한 채로 외부에 살아나가면 렉시컬 환경이 GC되지 않는다. **클로저의 작동 원리와 메모리 누수의 원리가 같은 현상**이다. 누수가 되는 조건은 "의도하지 않은 연장":

- `removeEventListener` 누락 → 핸들러가 캡처한 스코프 전체가 DOM 노드까지 함께 살아남음
- `clearInterval` 누락
- 클로저에 필요 없는 거대한 데이터까지 같은 스코프에서 캡처 → **스코프를 좁게 쪼개면 해결**
- React `useEffect` 클린업 누락

→ **스코프를 작게 쪼개는 것이 성능 기법이 되는 지점**이라는 감각.

**소멸은 언제 실제로 일어나나 — GC는 결정적인가?**

아니다. JS의 GC는 **비결정적**이다. unreachable이 되면 "회수될 자격을 얻는" 것이고 시점은 엔진이 정한다.

- 개발자가 GC를 강제할 수 없다 (`delete`는 프로퍼티 삭제, `null` 할당은 참조 끊기일 뿐)
- 그래서 메모리 프로파일링이 필요하다 — 코드만 봐서는 판정 불가
- 반대로 **파일 핸들 · 소켓 · 타이머 · 리스너 같은 자원은 GC에 맡기면 안 된다.** 명시적 해제 필요

정리: **"메모리는 GC가 알아서 한다"는 참이지만 자원 관리에는 적용되지 않는다.** 이게 `useEffect`가 클린업 함수를 반환하는 이유의 근거.

<details>
<summary>JS Symbol → TS unique symbol → Branded Types (연결 관계)</summary>

> ⚠️ **먼저 오해 정리.** 이 세 개는 한 덩어리가 아니다. Symbol과 `unique symbol`은 직접 연결되지만, **Branded Types는 Symbol과 거의 상관없다.** 심벌을 "더 안전한 키"로 빌려 쓴 것일 뿐, 문자열 키로도 완전히 성립한다.

### 개념 플로우

```plaintext
[JS Symbol] ── 런타임 값. 유일한 프로퍼티 키. 이름 충돌 방지 (6장)
     │
     │  "이 유일성을 타입으로도 표현해야 한다"
     ▼
[TS unique symbol] ── 타입. "이 선언의 그 심벌"을 특정
     │                 심벌 키 프로퍼티를 타입으로 쓰려면 필수
     │  ★ 여기까지가 직접적 연결
     │
     │  응용: 아무도 접근 못 하는 유일한 키가 필요한 곳에 재활용
     ▼
[Branded Types] ── 원시 타입에 가짜 표시를 붙여 구별시키는 패턴
                   ★ 심벌 없어도 됨. 문자열 키로도 동작
```

### 1단계 — JS Symbol (6장)

"세상에 하나뿐인 열쇠". 이름이 같아도 다른 값이다.

```javascript
Symbol("key") === Symbol("key"); // false

const secret = Symbol("secret");
const user = { name: "지연", [secret]: "비밀" };
user[secret]; // '비밀' — 이 열쇠를 가진 쪽만 열 수 있다
```

**존재 이유:** 문자열 키는 남이 실수로 덮어쓸 수 있다. 라이브러리가 남의 객체에 메타데이터를 붙일 때 `obj.id = ...`는 위험하고 `obj[mySymbol] = ...`는 안전하다. `Object.keys` · `for...in` · `JSON.stringify`에도 안 나와서 기존 코드를 깨뜨리지 않는다.

### 2단계 — TS `unique symbol` (진짜 연결점)

TS는 `Symbol()` 결과를 전부 `symbol` 타입으로 본다. 그러면 서로 다른 심벌을 타입에서 구별할 수 없다.

```typescript
const keyA: unique symbol = Symbol();
const keyB: unique symbol = Symbol();

type Config = { [keyA]: string; [keyB]: number }; // unique symbol이어야 가능
```

**한 줄 정의:** `unique symbol`은 **Symbol의 "런타임 유일성"을 타입 시스템으로 옮겨온 것.** 그래서 `const` 선언만 이 타입을 가질 수 있다 — `let`은 값이 바뀔 수 있어서 "그 심벌"을 특정할 수 없다.

### 3단계 — Branded Types (심벌과 무관한 별개 주제)

문제는 TS가 **구조적 타이핑**이라는 것. 모양만 같으면 통과한다.

```typescript
type UserId = string;
type PostId = string;
getUser("post_1" as PostId); // ✅ 통과해버린다
```

해법은 "가짜 프로퍼티를 붙여 모양을 다르게 만들기". **심벌 없이 문자열로도 된다.**

```typescript
type UserId = string & { __brand: "UserId" };
type PostId = string & { __brand: "PostId" };
getUser("post_1" as PostId); // ❌ 이제 막힌다
```

`__brand`는 **런타임에 존재하지 않는다.** 컴파일하면 그냥 문자열이라 **런타임 비용 0**.

심벌로 바꾸면 개선되는 3가지 — 필수가 아니라 개선이다:

- 자동완성에 `__brand`가 안 뜬다
- 다른 라이브러리와 브랜드 이름 충돌이 원리적으로 불가능
- 사용자가 손으로 위조하기 어렵다

### 관통하는 하나

세 층 모두 같은 문제를 푼다 — **"충돌하지 않는 유일한 식별자가 필요하다."**

| 층                        | 무엇으로부터 충돌을 막나                    |
| ------------------------- | ------------------------------------------- |
| JS Symbol (런타임)        | 다른 코드가 붙인 프로퍼티 키                |
| TS `unique symbol` (타입) | 다른 심벌과 타입 수준에서 섞이는 것         |
| Branded Types (타입)      | 다른 라이브러리 · 다른 도메인의 브랜드 이름 |

### 장단점

**Symbol (런타임 값)**

- 👍 키 충돌 없음 / 기존 순회 API를 오염시키지 않음 / well-known symbol로 언어 동작 훅킹(`Symbol.iterator`, `Symbol.toPrimitive` 등)
- 👎 완전한 은닉은 아님(`Object.getOwnPropertySymbols()`로 접근 가능 — 진짜 은닉은 클래스 프라이빗 필드) / 직렬화되지 않음 / 디버깅 시 눈에 안 보여 추적이 어려움

**Branded Types (타입 전용)**

- 👍 의미가 다른 같은 원시 타입의 혼용을 컴파일 타임에 차단 / 런타임 비용 0 / 검증 여부를 타입으로 추적 / 시그니처가 문서가 된다
- 👎 생성 지점에 `as`가 필요(= 타입 시스템에 거짓말) / 에러 메시지가 못생겨진다 / `JSON.parse` 경계에서 브랜드가 사라진다 / 팀 학습 곡선 / 과용하면 타입 곡예

**적용 범위는 좁게:** ID, 검증된 문자열(이메일 · URL), 단위 있는 숫자(초 vs 밀리초). 여기서 시작하고 늘리지 않는다.

### 💭 왜 고민할 가치가 있나

**(1) "런타임에 있는 것"과 "타입에만 있는 것"을 구분하는 훈련이다.**

Symbol은 런타임에 실재하고, 브랜드는 실재하지 않는다. 이 구분이 안 되면 `as User`를 검증이라고 착각한다. TS 타입은 컴파일 후 완전히 사라진다(type erasure) — **런타임은 여전히 100% 동적 타입.** API 응답 · `localStorage` · URL 파라미터에 대해 `interface`는 아무것도 보장하지 않는다.

→ 실전 결론: **런타임 검증(zod) + 브랜드(타입 증명서)가 한 쌍.** 검증 지점을 한 곳으로 몰고(Smart Constructor) 거기서만 브랜드를 부여하면 검증 누락이 컴파일 에러가 된다. `zod`의 `.brand()`가 이걸 지원한다.

**(2) "언어가 안 주는 걸 사용자가 흉내내는 것"의 비용을 보게 된다.**

명목적 타이핑을 Haskell(`newtype`) · Rust(newtype pattern) · Flow(`opaque type`)는 일급 기능으로 준다. TS는 안 준다 — 기존 JS에 점진적으로 얹으려면 구조적 타이핑이 필요했기 때문. 브랜드는 그 빈자리를 타입 레벨 해킹으로 메꾼 것이고 `as`라는 대가가 붙는다. **"우아한 확장인가, 결함의 사용자 부담인가"** 를 판단해보는 게 이 주제의 진짜 수확.

**(3) 실무 우선순위 감각**

- **꼭:** JS Symbol이 왜 있는지 + well-known symbol
- **좋음:** Branded Types — 심벌과 무관하게 유용한 패턴
- **나중:** `unique symbol` 문법 자체 — 심벌 키 객체 타입을 직접 쓸 일은 실무에서 드물다

# 04Ch-변수

## 변수와 식별자

### 변수

- 하나의 값을 저장하기 위해 확보한 메모리 공간 자체
- 그 메모리 공간을 식별하기 위해 붙인 이름
- 값의 위치를 가리키는 상직적인 이름
- `let variable = 123` ⇒ `키워드 변수명 = 값` 의 형태
  - 변수명은 메모리상의 주소를, 값은 주소에 해당하는 값을 의미함
  - 메모리상 값은 언제든 변경이 가능

### 식별자

변수 이름을 의미하며, 어떤 값을 구별해서 식별할 수 있는 고유한 이름을 의미

- 식별자는 값이 아닌 메모리 주소를 기억 → 즉, 식별자는 메모리 주소에 붙인 이름과 같음
- 변수 선언을 통해 JS 엔진이 식별자를 감지

## 변수 선언

- 변수를 생성하는 것
- 값을 저장하기 위한 메모리 공간을 확보 후, 확보된 메모리 공간의 주소를 연결하여 값을 저장할 수 있도록 준비
- 변수를 사용하기 위해 반드시 필요하며 var, let, const 키워드가 존재
- 선언 단계 후 초기화 단계를 거침
  - 선언 단계: 변수 이름을 등록하여 JS 엔진에 변수의 존재를 알림
  - 초기화 단계: 값을 저장하기 위한 메모리 공간을 확보하고 암묵적으로 undefined를 할당하여 초기화함
- 변수 호이스팅: 변수 선언문이 코드의 가장 처음에 위치한 것처럼 동작하는 JS 고유의 특징
  - 즉, 자바스크립트 엔진은 변수 선언이 어디에 위치하든 다른 코드보다 먼저 실행함
  - 변수 선언 - 런타임 이전, 값의 할당 - 런타임시 실행

### 변수 재할당

변수에 값을 재할당시 이전 값이 저장되어 있던 메모리 공간에 새로운 값을 저장하는 것 ❌
→ 새로운 메모리 공간을 확보하고 해당 메모리 공간에 새로운 값을 저장 🙆‍♀️

이때, 아무도 사용하지 않는 메모리를 해제 해주는 **가비지 콜렉터**를 통해 메모리 누수를 방지

# 05Ch-표현식과 문

## 값

표현식이 평가되어 생성된 결과로, 변수에 할당되는 것

## 리터럴

사람이 이해할 수 있는 문자 또는 약속된 기호를 사용해 값을 생성하는 표기법으로, JS엔진에 의해 런타임에 평가되어 값을 생성

### 표현식

값으로 평가될 수 있는 문으로, 표현식이 평가되면 새로운 값을 생성하거나 기존 값을 참조

- 리터럴도 평가되어 값을 생성하므로 그 자체가 표현식
- 식별자 참조는 값을 생성하지는 않지만 값으로 평가되므로 표현식

### 표현식과 값은 동치

표현식과 표현식이 평가된 값은 동등한 관계(동치)이므로 표현식은 **값처럼 사용할 수 있음**

- 수학에서 1 + 2가 3과 동치인 것과 같은 원리
- 즉, **값이 위치할 수 있는 자리에는 표현식도 위치할 수 있음**
- 따라서 표현식은 다른 표현식의 일부가 되어 새로운 값을 만들어낼 수 있음

```javascript
// 리터럴 표현식
10;
("Hello");

// 식별자 표현식
sum;
person.name;
arr[1];

// 연산자 표현식
10 + 20;
sum = 10;
sum !== 10;

// 함수·메서드 호출 표현식
square();
person.getName();
```

## 문

프로그램을 구성하는 기본 단위이자 최소 실행 단위로, 해당 문들의 집합으로 이루어진 것을 프로그램이라 칭함

- 명령문이라고도 부름
- 선언문, 할당문, 조건문, 반복문 등으로 구분

### 토큰

문법적인 의미를 가지며, 문법적으로 더 이상 나눌 수 없는 코드의 기본 요소를 의미

- 키워드, 식별자, 연산자, 리터럴, 세미콜론(;)이나 마침표(.) 같은 특수 기호가 모두 토큰에 해당
- `var sum = 1 + 2;` → var / sum / = / 1 / + / 2 / ; 총 7개의 토큰으로 구성된 1개의 문

## 세미콜론과 세미콜론 자동 삽입 기능(ASI)

세미콜론(;)은 문의 종료를 나타내며, JS 엔진은 세미콜론으로 문이 종료한 위치를 파악해 순차적으로 하나씩 문을 실행

- 단, 코드 블록(중괄호로 묶은 부분) 뒤에는 세미콜론을 붙이지 않음
  - 코드 블록은 언제나 문의 종료를 의미하는 **자체 종결성(self closing)** 을 갖기 때문
  - if문, for문, 함수 선언문 등의 코드 블록이 해당
- 문의 끝에 붙이는 세미콜론은 생략 가능
  - JS 엔진이 문의 끝이라고 예측되는 지점에 세미콜론을 자동으로 붙여주는 **ASI(automatic semicolon insertion)** 가 암묵적으로 수행되기 때문

### ASI의 동작이 개발자의 예측과 어긋나는 경우

```javascript
function foo() {
  return;
  {
  }
  // ASI 동작 결과  => return; {};
  // 개발자의 예측  => return {};
}
console.log(foo()); // undefined

var bar = (function () {})(function () {})();
// ASI 동작 결과  => var bar = function () {}(function () {})();
// 개발자의 예측  => var bar = function () {}; (function () {})();
// TypeError: (intermediate value)(...) is not a function
```

- 세미콜론을 붙여야 한다는 주장이 다수이며, ESLint 같은 정적 분석 도구도 세미콜론 사용을 기본으로 설정하고 있고 TC39 역시 ASI에 의존하지 말고 세미콜론을 붙이도록 권고

## 표현식인 문과 표현식이 아닌 문

표현식은 문의 일부일 수도 있고 그 자체가 문이 될 수도 있으며, 구분 기준은 **값으로 평가될 수 있는지**

- 변수 선언문: 값으로 평가될 수 없음 → 표현식이 아닌 문
- 할당문: 할당한 값으로 평가됨 → 그 자체가 표현식이면서 완전한 문 → 표현식인 문

### 구분하는 가장 간단한 방법 - 변수에 할당해보기

표현식인 문은 값으로 평가되므로 변수에 할당할 수 있지만, 표현식이 아닌 문은 할당하면 에러가 발생

```javascript
var x;                // 표현식이 아닌 문
var foo = var x;      // SyntaxError: Unexpected token var

x = 100;              // 표현식인 문(할당문)
var foo = x = 100;    // 값처럼 사용 가능
console.log(foo);     // 100
```

### 완료 값(completion value)

- 크롬 개발자 도구에서 **표현식이 아닌 문**을 실행하면 언제나 undefined가 출력되는데, 이를 완료 값이라 함
- 완료 값은 **표현식의 평가 결과가 아님** → 다른 값과 같이 변수에 할당할 수도, 참조할 수도 없음
- 반대로 표현식인 문을 실행하면 언제나 평가된 값을 반환
- 즉, 값으로 평가되는지의 판별은 콘솔 출력이 아니라 **변수 할당**으로 해야 함

# 06Ch-데이터 타입

- 데이터 타입이 필요한 이유
  - 값 저장시) JS 엔진은 값의 종류에 따라 정해진 크기의 메모리 공간을 확보
  - 값 참조시) 한 번에 읽어야할 메모리 공간의 크기를 알아야하는데, 이때 변수에 할당된 타입을 확인함
  - 메모리에서 읽어 들인 2진수를 어떻게 해석할지 결정하기 위해
- `심벌 테이블` : 식별자를 키로 바인딩된 값의 메모리 주소, 데이터 타입, 스코프 등을 관리하는 자료구조중 하나

## 원시 타입

1. 숫자 타입: 숫자, 정수와 실수 구분 없이 하나의 숫자 타입만 존재
   - 하나의 숫자 타입만 존재(정수, 실수 등 포함하여 하나로만 표현)
   - Infinity: 양의 무한대, -Infinity: 음의 무한대, NaN: 산술 연산 불가
2. 문자열 타입: 텍스트 데이터를 나타냄
   - 템플릿 리터럴 `` `${변수} 문자` `` 와 같은 사용이 가능
   - 문자열끼리 + 연산자를 사용해 연결 가능
3. 불리언 타입: 논리적 참(true)과 거짓(false)
   - 조건문에서 많이 사용됨
4. undefined 타입: var 키워드로 선언된 변수에 암묵적으로 할당되는 값
   - 변수 선언에 의해 확보된 메모리 공간에 처음으로 할당될 때까지 undefined가 반환됨
   - 변수 참조시 undefined가 반환되면 참조한 변수가 선언 이후 초기화되지 않았음을 확인할 수 있음!
   - 때문에 의도적으로 할당시 undefined의 본래 취지를 줄이기 위해 `null`을 할당함
5. null 타입: 값이 없다는 것을 의도적으로 명시할 때 사용하는 값
   - 변수에 null 할당 === 변수에 값이 없다는 것을 의도적으로 명시할 때 사용
6. 심벌 타입: 변경 불가능한 원시 타입의 값
   - 다른 값과 중복되지 않는 유일한 값으로, 이름이 충돌할 위험이 없는 객체의 유일한 프로퍼티 키를 만들기 위해 사용
   - Symbol 함수를 호출해 사용
   - 생성된 심벌값은 외부에 노출되지 않으며, 다른 값과 절대 중복되지 않음

     ```typescript
     // 심벌 값 생성
     var key = Symbol("key");

     // 객체 생성
     var obj = {};
     ```

## 동적 타입과 정적 타입 언어

### 정적 타입

- 변수 선언시 데이터 타입을 사전에 선언해야하는 것으로, 명시적 타입 선언이라 한다
- 변수에 선언한 타입에 해당되는 값만 할당 가능
- `컴파일` 시점에서 타입 체크

### 동적 타입

- 선언이 아닌 할당에 의해 타입이 결정됨
- 재할당에 의해 변수의 타입은 언제든지 변할 수 있음
- JS는 동적 타입에 해당되며, 개발자의 의도와 상관없이 JS 엔진에 의해 타입이 자동적으로 변환되는 문제가 있기도함
  - 변수의 개수 최소한으로 줄이기
  - 변수의 유효 스코프 좁히기
  - 전역 변수 사용 줄이기
  - 변수보단 상수를 사용하여 값의 변경을 방지하기

# 07Ch-연산자

- 연산자: 하나 이상의 표현식을 대상으로 산술, 할당, 비교 등을 수행하여 하나의 값을 만듦
- 피연산자: 연산의 대상

## 산술 연산자

피연산자를 대상으로 수학적 계산을 수행하여 새로운 숫자 값을 만듦

- 산술 연산이 불가능한 경우, NaN을 반환

### 이항 산술 연산자

2개의 피연산자를 산술 연산하여 숫자 값을 만드는 것으로 `+`, `-`, `*`, `/`, `%` 등이 있다

### 단항 산술 연산자

1개의 피연산자를 산술 연산하여 값을 만드는 것으로 `++`, `--`, `+`, `-`(반전한 값)이 있다

```typescript
var before = 5;

// 선할당 후증가
after = before++;

console.log(before, after); // 6 7

// 선증가 후할당
after = ++before;
console.log(before, after); // 7 7
```

## 할당 연산자

우항에 있는 피연산자의 평가 결과를 좌항에 있는 변수에 할당하며, 변수 값이 변하는 부수 효과가 있다

ex) `=`, `+=`, `-=`, `*=`, `/=`, `%=`

## 비교 연산자

좌항과 우항의 피연산자를 비교한 다음 그 결과를 불리언 값으로 변환

- if문, for문과 같은 제어문의 조건식에서 주료 사용함

ex) `==`, `===`, `!=`, `!==` 이때, `===`와 `!==`는 값과 타입까지 비교하므로 더 예측하기 쉬움. 단, NaN의 경우 자신과 일치하지 않는 유일한 값이므로 특정 숫자가 NaN인지를 조사하기 위해선 `Number.isNaN`을 사용해야한다

## 삼항 조건 연산자

`조건식 ? 조건식이 true일 때 반환할 값 : 조건식이 false일 때 반환할 값`과 같은 조건문으로, if-else문을 사용해서도 유사하게 처리할 수 있다. 단, if-else문은 삼항 조건 연산자와 같이 값처럼 사용이 불가능함

```typescript
var a = 2;

// 2 % 2는 0이고 0은 false이므로 암묵적 타입 변환이 됨
var result = a % 2 ? "홀수" : "짝수";

if (x % 2) result = "홀수";
else result = "짝수";
```

## 논리 부정 연산자

- `||` 논리합(OR)
  - 좌항에서 우항으로 평가됨
  - 표현식을 평가하는 도중에 평가 결과가 확정된 경우 나머지 평가 과정을 생략
- `&&` 논리곱(AND)
  - 좌항에서 우항으로 평가됨
  - 표현식을 평가하는 도중에 평가 결과가 확정된 경우 나머지 평가 과정을 생략
- `!` 부정(NOT)
  - 언제나 `boolean` 값을 반환 (ex. `!0` → true , `!'hi'` → false)
