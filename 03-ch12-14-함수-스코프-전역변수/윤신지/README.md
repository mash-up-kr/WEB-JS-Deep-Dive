# 12장. 함수

## 함수란?

> 프로그래밍 언어의 **함수는 일련의 과정을 문으로 구현하고 코드 블록으로 감싸서 하나의 실행 단위로 정의한 것**이다.



자바스크립트의 함수 사용법은 아래와 같다.

```javascript
// 함수 정의
function add(x, y) {
  return x + y;
}

// 함수 호출
var result = add(2, 5);

// 함수 add에 2, 5를 전달하고 반환값 7을 반환
console.log(result);  // 7
```



## 함수를 사용하는 이유

**코드의 재사용**이 함수를 사용하는 가장 큰 목적이다. 동일한 작업을 여러 번 수행해야 할 때 함수로 만들어두면, 코드의 중복을 제거하고 **유지보수성**을 높일 수 있다. 

또한 함수는 **코드에 이름을 붙이는 행위**이기도 하기 때문에, 함수명은 그 자체로 코드가 무엇을 하는지 설명해 주는 문서 역할을 한다.



## 함수 리터럴

함수도 객체이기 때문에 리터럴 표기법으로 생성할 수 있다. 리터럴은 값을 생성하기 위한 표기법으로, 함수 리터럴도 평가되어 값을 생성한다. 즉, 이 값은 객체고 **함수는 객체다.**

일반 객체 리터럴과 다른 점은, 함수 리터럴은 `function` 키워드, 함수 이름(생략 가능), 매개변수 목록, 함수 몸체로 구성된다는 것이다. 

```javascript
const add = function (x, y) {
  return x + y;
};
```



- 함수 이름
  - 함수 이름은 식별자다. 따라서 식별자 네이밍 규칙을 준수해야 한다.
  - 함수 이름은 함수 몸체 내에서만 참조할 수 있는 식별자다.
  - 함수 이름은 생략할 수 있으며, 이름이 있는 함수를 기명 함수, 이름이 없는 함수를 무명/익명 함수라 한다.

  
- 매개변수 목록
  - 0개 이상의 매개변수를 소괄호로 감싸고 쉼표로 구분한다.
  - 각 매개변수에는 함수를 호출할 때 지정한 인수가 순서대로 할당된다. =&gt; 매개변수 목록은 순서에 의미가 있다.
  - 매개변수는 함수 몸체 내에서 변수와 동일하게 취급된다. =&gt; 매개변수도 변수와 마찬가지로 식별자 네이밍 규칙을 준수해야 한다.
- 함수 몸체
  - 함수가 호출되었을 때 일괄적으로 실행될 문들을 하나의 실행 단위로 정의한 코드 블록이다.
  - 함수 몸체는 함수 호출에 의해 실행된다.



## 함수 정의

### 함수 선언문

```javascript
function add(x, y) {
  return x + y;
}
```

함수 선언문은 함수 이름을 생략할 수 없다. 겉보기엔 표현식이 아닌 것 같지만, 사실 **함수 선언문은 표현식이 아닌 문**이다. 

- 문 : 프로그램을 구성하는 기본 단위이자 최소 실행 단위
- 표현식 : 값으로 평가될 수 있는 문

즉, 함수 선언문은 값으로 평가될 수 없다. 함수 선언문을 개발자 도구에서 실행하면 완료 값으로 `undefined`가 출력된다. 표현식이 아니기 때문에 **변수에 할당할 수 없다.** 



그렇다면 위의 함수 리터럴에서 함수를 변수에 할당한 경우는 무엇일까...!! 기명 함수 리터럴이 중의적으로 사용되기 때문에 가능하다.



**중의적인 표현 { }**

자바스크립트에서 {}은 **블록문**일 수도, **객체 리터럴**일 수도 있다. 자바스크립트 엔진은 중의적인 코드는 **코드의 맥락**에 따라 해석이 달라진다.

- {}이 단독으로 존재하는 경우 : 블록문으로 해석
- {}이 값으로 평가되어야 할 문맥에서 피연산자로 사용되는 경우 : 객체 리터럴로 해석

=&gt; 동일한 코드도 코드의 문맥에 따라 해석이 달라질 수 있다. 



**기명 함수 리터럴**

{}와 동일하게 **함수 이름이 있는 함수 리터럴**도 중의적인 표현으로 코드의 맥락에 따라 해석된다. 두 가지 모두 공통적으로 **함수가 생성**되지만, 함수를 생성하는 **내부 동작에 차이가 존재**한다. 

- 함수 선언문으로 해석되는 경우 : 피연산자로 사용되지 않고 **단독**으로 사용
- 함수 리터럴로 해석되는 경우 : 값으로 평가되어야 하는 문맥(변수 할당, 피연산자로 사용)



**함수 리터럴 VS 함수 선언문**

```javascript
// 함수 선언식 : 단독으로 사용되어 함수 선언식으로 해석됨
function foo(){console.log('foo');}
foo(); // foo

// 함수 리터럴 : ( ) 연산자의 피연산자로 사용되어 기명 함수 리터럴로 해석됨
( function bar(){console.log('bar');} )
bar(); // ReferenceError: bar is not defined
```

위 예제에서 단독으로 사용된 함수 리터럴(foo)는 함수 선언문으로 해석된다. 하지만 그룹 연산자 () 내에 있는 함수 리터럴(bar)는 함수 선언문으로 해석되지 않고 함수 리터럴 표현식으로 해석된다. 그룹 연산자의 피연산자는 값으로 평가될 수 있는 표현식이어야 하지만, 표현식이 아닌 문인 함수 선언문은 피연산자로 사용할 수 없기 때문이다.

위 예제는 함수가 생성되었다는 점은 동일하지만 **함수 호출**에는 차이점을 보인다. 

함수 리터럴의 **함수 이름**은 **함수 몸체 내에서만 참조할 수 있는 식별자**이기 때문이다. 그렇기 때문에 함수 몸체 외부에서는 함수 이름 bar로 함수를 호출할 수 없다.   
=&gt; 즉, `bar` 함수는 호출할 수 없다.

함수 선언문으로 정의된 함수는 `foo`로 호출되었다. `foo`는 함수 내부에서만 유효하고, 변수 이름을 할당한 적도 없는데 어떻게 호출이 가능했을까?  
=&gt; `foo`는 자바스크립트 엔진이 **암묵적으로 생성한 식별자** 덕분에 가능하다.



**암묵적으로 생성된 식별자**

> 함수가 정의되면, 자바스크립트 엔진은 함수 선언문을 해석하여 함수 객체를 생성한다. 

함수 이름은 함수 몸체 내부에서만 유효한 식별자이므로 함수 이름과는 별도로 생성된 함수 객체를 가리키는 **식별자**가 필요하다.   
=&gt; 정의된 함수를 호출하기 위해서 자바스크립트 엔진은 암묵적으로 **함수 이름과 동일한 식별자를 생성하여 함수 객체에 할당**한다.



우리는 **함수 이름**으로 함수를 호출하는 것이 아니라 함수 객체를 가리키는 **식별자**로 호출한다. 즉, 함수 선언문으로 생성한 함수를 호출하는 것은 함수 이름 add가 아니라 자바스크립트 엔진이 암묵적으로 생성한 식별자 add인 것이다. 



### 함수 표현식

자바스립트의 함수는 **일급 객체**다. 함수가 일급 객체라는 것은 함수를 값처럼 자유롭게 사용할 수 있다는 의미이다. 

```javascript
const add = function (x, y) {
  return x + y;
};
```

함수를 값처럼 변수에 할당하는 방식이다. 이때 함수 이름은 생략할 수 있는데, 이런 함수를 **익명 함수**라고 한다.

일급 객체란 다음 조건을 만족하는 값이다.

- 변수에 할당할 수 있다
- 함수의 매개변수로 전달할 수 있다

- 런타임에 동적으로 생성할 수 있다

JavaScript의 함수는 이 4가지를 모주 만족한다. 때문에 함수를 값처럼 변수에 담고, 다른 함수에 인자로 넘기고(콜백), 함수가 함수를 반환(클로저, 고차함수)할 수 있는 것이다. 

=&gt; React의 커스텀 훅, Redux의 미들웨어, Express의 라우터 핸들러 등 현대 자바스크립트 생태계의 핵심 패턴들은 전부 함수가 일급 객체라는 성질 위에서 동작한다.

<details class="orca-details">
<summary>함수 선언문 VS 함수 표현식</summary>

함수 선언문과 함수 표현식은 비슷하게 생겼지만 동작 방식이 다르다. 

```javascript
// 함수 선언문 - 호출 가능
console.log(add(1, 2)); // 3
function add(x, y) {
  return x + y;
}

// 함수 표현식 - 에러 발생
console.log(sub(5, 2)); // TypeError: sub is not a function
var sub = function (x, y) {
  return x - y;
};
```

함수 선언문은 런타임 이전 단계에서 함수 객체가 생성되고 식별자에 할당까지 완료된다. 반면 함수 표현식은 변수에 할당되는 값이므로, **변수 호이스팅 규칙**을 따른다. 즉, `var sub`이라는 선언만 먼저 끌어올려지고, 실제 함수 할당은 코드가 그 줄에 도달했을 때 이루어진다. 

이런 이유로 많은 스타일 가이드는 호이스팅으로 인한 예측 불가능한 동작을 줄이고, 코드를 위에서 아래로 읽었을 때의 흐름과 실제 실행 순서를 일치시키기 위해 함수 표현식 사용을 권장한다.

</details>



### 함수 생성 시점과 함수 호이스팅

```javascript
// 함수 참조
console.dir(add); // f add(x,y)
console.dir(sub); // undefined

// 함수 호출
console.log(add(2, 5)); // 7
console.log(sub(2, 5)); // TypeError: sub is not defined

// 함수 선언문
function add(x,y){ return x + y; }
// 함수 표현식
var sub = function (x,y){ return x - y; }
```

위 예제에서 **함수 선언 이전에 호출이 가능한 함수 선언문**과 **함수 정의 이전엔 호출이 불가능한 함수 표현식**의 차이점을 알 수 있다. 



**함수 호이스팅**

자바스크립트의 모든 선언문은 런타임 이전에 자바스크립트 엔진에 의해 **먼저 실행**된다. 즉, 함수 선언문으로 함수를 정의하면 **런타임 이전에 함수 객체가 먼저 생성**된다. 그리고 자바스크립트 엔진은 함수 이름과 동일한 **식별자를 암묵적으로 생성하고 생성된 함수 객체를 할당**한다.

즉, 코드가 순차적으로 실행되는 런타임에는 이미 함수 객체가 생성되어 있고 함수 이름과 동일한 식별자에 할당까지 완료된 상태이다.   
=&gt; 함수 선언문 이전에 함수를 참조, 호출할 수 있다. 

이처럼 함수 선언문이 **코드의 선두로 끌어 올려진 것처럼 동작하는 자바스크립트 고유의 특징을 함수 호이스팅**이라고 한다. 



**변수 호이스팅**

var 키워드로 선언된 변수는 **런타임 이전에 변수가 선언되어 undefined로 초기화**된다. 그리고 **런타임에 변수에 값이 할당**된다. 즉, var 키워드를 사용한 변수 선언문 이전에 변수를 참조하면 undefined로 평가되어 참조가 불가능하다.



함수 호이스팅과의 공통점/차이점

- 공통점
  - JS 엔진에 의해 런타임 이전에 먼저 실행되어 식별자를 생성한다
- 차이점
  - 변수는 undefined로 초기화되고, 함수 선언문의 식별자는 함수 객체로 초기화된다.  
  변수 선언문 이전에 변수 참조 =&gt; 변수 호이스팅에 의해 undefined로 평가  
  함수 선언문 이전에 함수 호출 =&gt; 함수 호이스팅에 의해 호출 가능



<details class="orca-details">
<summary>`var` 변수 호이스팅과 함수 호이스팅은 뭐가 다를까?</summary>

`var`로 선언한 변수는 호이스팅 시 `undefined`로 초기화된다. 그래서 선언 전에 접근하면 값은 `undefined`이지만 에러는 나지 않는다. 반면 **함수 선언문은 호이스팅 시 선언과 초기화(함수 객체 할당)가 한 번에 이루어진다.** 그래서 선언 이전 코드에서 호출해도 정상적으로 함수가 실행된다.

이 차이 때문에 함수 호이스팅은 코드의 실행 순서를 예측하기 어렵게 만든다는 비판을 받기도 한다. 이런 이유로 실무에서는 파일 최상단에 함수를 몰아서 선언하거나, 아예 함수 표현식/화살표 함수 + `const`를 사용해 호이스팅의 모호함을 원천 차단하는 스타일을 선호하는 경우가 많다.

</details>



### Function 생성자 함수

자바스크립트가 기본 제공하는 빌트인 `Function` 생성자 함수에 매개변수 목록과 함수 몸체를 문자열로 전달하면서 `new` 연산자와 함께 호출하면 **함수 객체를 생성해서 반환**한다. 

```js
// 함수 생성자 함수 정의
function MyFunction(name) {
  this.name = name; // 함수의 속성으로 이름을 설정
  this.sayHello = function() {
    console.log('Hello, ' + this.name + '!');
  };
}

// 함수 생성자를 사용하여 객체 생성
var myObject = new MyFunction('John');

// 객체의 메서드 호출
myObject.sayHello(); // 출력: Hello, John!
```

 Function 생성자 함수는 클로저를 생성하지 않고, 이 함수는 함수 선언문/함수 표현식으로 생성한 함수와 다르게 동작하지 않기 때문에 권장하지 않는다고 한다.



### 화살표 함수

ES6에서 도입된 함수로, function 키워드 대신 화살표 =&gt; 를 사용해 함수를 간략한 방법으로 선언할 수 있다. 화살표 함수는 항상 **익명 함수**로 정의한다. 

화살표 함수는 기존의 함수보다 표현만 간략한 것이 아니라 내부 동작 또한 간략화되이ㅓ 있다. 함수선언문/함수표현식을 완벽히 대체할 수 없다. 

- 함수 선언문/함수 표현식과 차이점
  - this 바인딩
    - 일반 함수 : 호출 방식에 따라 동적 결정
    - 화살표 함수 : 상위 스코프의 `this`를 그대로 사용
  - arguments 객체
    - 일반 함수 : 있음
    - 화살표 함수 : 없음
  - 생성자 함수로 사용
    - 일반 함수 : 가능
    - 화살표 함수 : 불가능
  - prototype 프로퍼티
    - 일반 함수 : 있음
    - 화살표 함수 : 없음

<summary>화살표 함수는 this를 안 만든다는 게 정확히 무슨 뜻일까?</summary>

책에서는 26.3절에서 자세히 살펴보자고 하지만... 그래도 간단히 알아보면

일반 함수는 호출될 때마다 자신만의 `this`를 새로 바인딩한다. 반면 화살표 함수는 자신만의 `this`를 가지지 않고,ㅎ ㅏㅁ수가 정의된 시점의 상위 스코프의 `this`를 그대로 이어받는다. 이 특성 덕분에 콜백 함수에서 `this`가 엉뚱한 대상을 가리키는 흔한 버그를 해결할 수 있다.

```js
class Timer {
  constructor() {
    this.seconds = 0;
  }
  start() {
    // 일반 함수였다면 setInterval 내부의 this는 전역 객체(또는 undefined)를 가리킴
    setInterval(() => {
      this.seconds++; // 화살표 함수라 Timer 인스턴스의 this를 그대로 사용
      console.log(this.seconds);
    }, 1000);
  }
}
```

다만 이 특성 때문에 **객체의 메서드로 화살표 함수를 정의하는 것은 지양**해야 한다. 메서드 내부에서 `this`가 그 객체를 가리키지 않고 상위 스코프를 가리키게 되기 때문이다.

## 함수 호출

함수는 함수를 가리키는 식별자와 함수 호출 연산자 ()로 호출한다. 함수를 호출하면 현재의 실행 흐름을 중단하고 호출된 함수로 실행 흐름을 옮긴다. 이때 매개변수에 인수가 순서대로 할당되고, 함수 몸체의 문들이 실행되기 시작한다. 



### 매개변수와 인수

함수 호출 시 함수 내부로 전달되어야 하는 값이 있는 경우, **매개변수(인자)**를 통해 인수를 전달한다. 



**인수**

- 함수를 호출할 때 지정
- 개수와 타입에 제한이 없음
- 표현식(값으로 평가가 가능한 문)이어야 함



**매개변수**  
함수가 호출될 때마다 암묵적 매개변수 생성 -&gt; undefined로 초기화 -&gt; 인수 순서대로 할당의 순서를 거침

- 함수를 정의할 때 선언
- 함수 몸체 내부에서 변수와 동일하게 취급
- 함수 몸체 내부에서만 참조가 가능하고, 함수 몸체 외부에서는 참조할 수 없음



**매개변수와 인수의 개수**

함수는 매개변수의 개수와 인수의 개수가 **일치하는지 확인하지 않는다.**

- 매개변수 개수 &gt; 인수 개수 : 할당되지 않은 매개변수의 값은 undefined가 됨
- 개매변수 개수 &lt; 인수 개수 : 초과된 인수는 무시됨  
초과된 인수는 그냥 버려지는 것이 아니라 암묵적으로 `arguments` 객체의 프로퍼티로 보관됨



### 인수 확인

```js
function add (x, y){
  return x + y;
}

console.log(add(2)); // NaN
console.log(add('a','b')); // 'ab'
```

위와 같은 상황에서 개발자의 의도는 숫자 2개를 더하고 싶었다고 하자. 이때, 코드상으로는 어떤 타입의 인수를 전달해야 하는지, 어떤 타입의 값을 반환해야 하는지 명확하지 않아 개발자가 원하는 값이 아님에도 오류는 발생하지 않으나 원하는 답을 얻지 못한다. 

- 자바스크립트 함수는 매개변수와 인수의 개수가 일치하는지 확인하지 않는다
- 자바스크립트는 동적 타입 언어다. 따라서 자바스크립트 함수는 매개변수의 타입을 사전에 지정할 수 없다.



**방법 1. 타입스크립트**

함수 내부에서 적절한 인수가 전달되었는지 확인하더라도, 부적절한 호출은 사전에 방지가 어렵기 때문에 런타임에 에러로 발생한다. 따라서 **정적 타입 선언**이 가능한 타입스크립트를 도입하여 컴파일 시점에 부적절한 호출을 방지할 수 있다.



**방법 2. arguments 객체**

arguments 객체를 통해 인수의 개수를 확인할 수 있다. 



**방법 3. 단축 평가로 기본값 할당**

인수가 전달되지 않은 경우, 단축 평가를 사용해 매개변수의 기본값을 할당할 수 있다. 

```js
function add(a, b, c){
  a = a || 0;
  b = b || 0;
  c = c || 0;
  return a + b + c;
}

console.log(add(1,2,3)); // 6
console.log(add(1,2)); // 3
console.log(add(1)); // 1
console.log(add()); // 0
인수확인방법 4. 매개변수 기본값
```



**방법 4. 매개변수 기본값**

ES6에서 도입된 매개변수 기본값을 사용하면, 함수 내에서 수행하던 인수 체크 및 초기화를 간소화할 수 있다. 다만 매개변수 기본값은 **매개변수에 인수를 전달하지 않았을 경우**와 **매개변수에 undefined**를 전달한 경우에만 유효하다. 



### 매개변수의 최대 개수

물리적 한계가 있으므로 최대 개수에 대한 제한이 있겠지만 명시적으로 제한하고 있지는 않으며, 물리적인인 제한도 신경 써야 할 정도로 제한이 있진 않다. 

하지만 매개변수는 함수 코드를 이해하는데 방해되는 요소라고 할 수 있으므로, 이상적인 매개변수는 0개이며 최대 3개를 넘지 않는 것을 권장한다.

그 이상의 매개변수가 필요하다면 객체로 전달하는 것이 유리하다. 객체를 인수로 사용하는 경우 프로퍼티 키만 정확히 지정하면 매개변수의 순서를 신경 쓰지 않아도 되므로 코드의 가독성도 좋아지고 실수도 줄어든다. 하지만 함수 내부에서 변경할 경우 부수효과가 발생하니 주의해야 한다.



### 반환문

반환문을 사용해 실행 결과를 함수 외부로 반환할 수 있다. 이때 return 키워드를 사용하여, 자바스크립트에서 사용 간으한 모든 값을 반환할 수 있다.



**반환문의 역할**

- 함수 실행을 중단하고 함수 몸체를 빠져나감
  - 반환문이 작성되어 있다면, 함수 실행이 중단되기 때문에 반환문 이후의 다른 문은 실행되지 않고 무시된다.
- 반환문은 retrun 키워드 뒤에 오는 표현식을 평가해 반환함
  - 이때  return 키워드 뒤에 반환값으로 사용할 표현식을 명시하지 않으면 undefined 반환
  - 반환식은 생략이 가능. 마지막 문까지 실행 후 암묵적으로 undefined 반환
  - return 키워드와 표현식 사이 줄바꿈이 있는 경우 세미콜론 자동 삽입 기능에 의해 세미콜론이 추가되어 의도치 않은 결과가 발생할 수 있다.



반환문은 함수 몸체 내부에서만 사용할 수 있다. 전역에서 반환문을 사용하면 문법 에러가 발생한다. 

참고로 Node.js는 모듈 시스템에 의해 파일별로 독립적인 파일 스코프를 갖기 때문에, 파일의 가장 바깥 영역에 반환문을 사용해도 에러가 발생하지 않는다. 



<details class="orca-details">
<summary>return문 뒤에 줄바꿈이 있으면 왜 문제가 생길까?</summary>

자바스크립트에는 **ASI(Automatic Semicolon Insertion, 세미콜론 자동 삽입)** 규칙이 있다. `return` 뒤에 줄바꿈이 오면, 엔진이 그 자리에 자동으로 세미콜론을 삽입해버린다.

```javascript
function getObject() {
  return
  {
    name: 'Lee'
  };
}

console.log(getObject()); // undefined !!
```

위 코드는 `return;`으로 해석되어 `undefined`를 반환한다. 그래서 객체를 반환할 때는 `return {` 처럼 여는 중괄호를 같은 줄에 두는 것이 안전한 습관이다. 화살표 함수로 객체 리터럴을 즉시 반환할 때도 `() => ({ name: 'Lee' })`처럼 소괄호로 감싸야 하는 이유와 본질적으로 같은 문제이다(화살표 함수 몸체의 `{}`와 객체 리터럴의 `{}`를 구분하기 위함).

</details>


# 13장. 스코프

## 스코프란?

자바스크립트에서는 

- var 키워드로 선언한 변수와 let, const 키워드로 선언한 변수의 스코프가 다르다.
- 스코프는 변수, 함수와 깊은 관련이 있다.



&nbsp;

12장에서 공부한 내용을 토대로, 함수의 매개변수는 함수 몸체 내부에서만 참조가 가능하다. 스코프가 함수 몸체 내부로 한정되기 때문이다. 변수 선언은 코드 블록 가장 바깥, 코드 블록, 함수 몸체 내에서도 가능하다.



```js
var var1 = 1; // 코드 블록 가장 바깥에서 변수 선언

if(true){
  var var2 = 2; // 코드 블록 내에서 변수 선언
  if(true) {
    var var3 = 3; // 중첩된 코드 블록 내에서 변수 선언
  }
}
function foo(){
  var var4 = 4; // 함수 내에서 변수 선언
  
  function bar(){
    var var5 = 5; // 중첩된 함수 내에서 변수 선언
  }
}

console.log(var1); // 1
console.log(var2); // 2
console.log(var3); // 3
console.log(var4); // ReferenceError: var4 is not defined
```

위처럼 변수는 자신이 선언된 위치에 의해 유효한 범위, 즉 **다른 코드가 변수 자신을 참조할 수 있는 범위**가 결정된다. 변수 뿐만 아니라 모든 식별자(변수 이름, 함수 이름, 클래스 이름 등)는 **자신이 선언된 위치에 의해 다른 코드가 식별자 자신을 참조할 수 있는 유효 범위**가 결정된다. 

=&gt; 이를 식별자가 유효한 범위, 즉 스코프라고 한다. 



**식별자 결정**

```js
var x = 'global'; // 1️⃣ 

function foo(){
  var x = 'local'; // 2️⃣ 
  console.log(x);
}

console.log(x); 
```

위 에제가 어떻게 동작할지 고민해보자. 코드의 가장 바깥 영역과 함수 내부에 같은 이름을 갖는 x 변수를 선언했고, 1과 2에서 x변수를 참조한다. 이때 자바스크립트 엔진은 이름이 같은 두 개의 변수 중에서 어떤 변수를 참조해야 할 것인지 결정해야 하는데, 이를 **식별자 결정**이라고 한다. 이때 자바스크립트 엔진은 식별자를 **스코프**라는 기준을 가지고 결정한다.   
=&gt; 따라서 스코프란 **자바스크립트 엔진이 식별자를 검색할 때 사용하는 규칙**이라고도 할 수 있다. 



> 코드가 어디서 실행되며 주변에 어떤 코드가 있는지를 **렉시컬 환경**이라고 부른다. 코드의 문맥은 **렉시컬 환경**으로 이루어진다. 이를 구현한 것이 **실행 컨텍스트**이며, 코든 코드는 실행 컨텍스트에서 평가되고 실행된다. 



<details class="orca-details">
<summary>스코프와 실행 컨텍스트는 같은 개념일까?</summary>

밀접하지만 다른 개념이다. 실행 컨텍스트는 코드가 실행되는 환경 자체(변수 정보, `this` 바인딩, 외부 렉시컬 환경 참조 등을 담은 자바스크립트 엔진 내부의 자료구조)를 말하고, 스코프는 그 실행 컨텍스트가 관리하는 **여러 정보 중 "식별자를 어디까지 찾을 수 있는가"에 해당하는 규칙/범위**이다. 실행 컨텍스트 내부의 "렉시컬 환경(Lexical Environment)"이라는 구성 요소가 스코프 체인을 구현하는 실질적인 메커니즘이다. 즉 스코프는 개념이고, 실행 컨텍스트(그 안의 렉시컬 환경)는 그 개념을 엔진이 실제로 구현하는 방식이라고 이해하면 된다.

</details>



위의 예제를 다시 살펴보면, 1️⃣에서 선언된 변수는 코드 바깥 영역에서 선언되었으므로 **어디서든** 참조가 가능하다. 2️⃣에서 선언된 변수는 **함수 내부**에서만 참조 가능하다. 

=&gt; 즉, 이름이 같은 두 개의 변수지만 스코프가 다른 별개의 변수이다. 만약 스코프라는 개념이 없었다면, 같은 이름을 갖는 변수는 충돌을 일으키므로 프로그램 전체에서 하나밖에 사용할 수 없었을 것이다. 



## 스코프의 종류

코드는 지역과 전역으로 구분된다.

- 전역 : 코드의 가장 바깥 영역
- 지역 : 함수 몸체 내부



### 전역과 전역 스코프

- 전역 : 코드의 가장 바깥 영역
  - 전역에 변수를 선언하면, 전역 스코프를 갖는 전역 변수가 됨
  - 전역 변수는 어디서든 참조 가능



### 지역과 지역 스코프

- 지역 : 함수 몸체 내부
  - 지역에 변수를 선언하면, 지역 스코프를 갖는 지역 변수가 됨
  - 지역 변수는 자신의 지역 스코프와 하위 지역 스코프에서 참조 가능



=&gt; 이때 중요한 성질은, 안에서는 밖을 볼 수 있지만, 밖에서는 안을 볼 수 없다는 것이다. 아래 예제의 경우 `inner` 함수는 자신을 감싸고 있는 `outer`와 전역의 변수를 모두 참조할 수 있지만, 반대로 `outer`는 `inner` 내부의 `innerLocal`에 접근할 수 없다. 

```js
const global = '전역 변수';

function outer() {
  const outerLocal = 'outer의 지역 변수';

  function inner() {
    const innerLocal = 'inner의 지역 변수';
    console.log(global);     // 접근 가능
    console.log(outerLocal); // 접근 가능
    console.log(innerLocal); // 접근 가능
  }
  inner();

  console.log(innerLocal); // ReferenceError - inner 내부 변수는 outer에서 접근 불가
}
```



<details class="orca-details" open>
<summary>전역 스코프에도 레벨이 있을까? 예를 들어 브라우저의 전역 객체(window)와 전역 스코프는 같은 건가?</summary>

브라우저 환경에서 `var`로 선언한 전역 변수나 암묵적 전역(선언 없이 값을 할당한 변수)은 실제로 전역 객체 `window`의 프로퍼티가 된다. 반면 `let`, `const`로 선언한 전역 변수는 **전역 스코프에는 속하지만** `window` **객체의 프로퍼티는 되지 않는다.** (이를 위해 별도의 "선언적 환경 레코드"에 저장됨). 이것이 바로 `var x = 1;` 후 `window.x`가 `1`을 출력하지만, `let y = 1;` 후 `window.y`는 `undefined`인 이유이다. 이 차이는 실무에서 전역 스코프 오염 여부를 디버깅할 때 매우 중요한 힌트가 된다.

</details>

## 스코프 체인

함수는 중첩될 수 있고, 이 중첩 관계에 따라 스코프도 계층 구조를 이룬다. 이렇게 여러 스코프가 사슬처럼 연결된 구조를 **스코프 체인**이라고 부른다. 

자바스크립트 엔진은 특정 식별자를 참조하려 할 때, **가장 안 쪽** 스코프부터 시작해서 **바깥쪽 스코프**로 차례차례 검색한다. 이를 **식별자 검색**이라고 한다. 



**스코프 체인**

변수를 참조할 때 자바스크립트 엔진은 스코프 체인을 통해, 변수를 참조하는 코드의 스코프에서 시작하여 상위 스코프 방향으로 이동하며 선언된 변수를 검색한다.

1. 변수를 참조하는 `코드의 스코프`에서 변수 검색
2. 없다면 그 `상위 스코프`에서 변수 검색
3. 없다면 반복
4. 최상위 스코프인 `전역 스코프`에서 변수 검색

```js
const x = 'global x';

function outer() {
  const x = 'outer x';

  function inner() {
    console.log(x); // 'outer x'
    // inner 스코프에는 x가 없음 → outer 스코프에서 검색 → 발견!
  }
  inner();
}
outer();
```

`inner` 함수 내부에서 `x`를 참조하면, 엔진은 다음 순서로 검색한다. 

1. `inner` 함수 스코프 → `x` 없음
2. `outer` 함수 스코프 → `x` = `'outer x'` 발견! 검색 종료
3. (만약 outer에도 없었다면) 전역 스코프까지 검색

이렇게 가장 가까운스코프에서 먼저 찾은 변수가 우선 적용되는 것을 **변수 섀도잉(Variable Shadowing)** 이라 한다. `outer`의 `x`가 전역의 `x`를 가린다(shadow)고 표현한다.



**렉시컬 환경** 

이러한 스코프 체인은 실제 물리적으로 존재한다. 자바스크립트 엔진은 코드를 실행하기 전에, 계층적 구조인 `렉시컬 환경`을 생성한다.

`변수 선언`이 실행되면, 변수 식별자가 렉시컬 환경(자료 구조)에 키로 등록되고, `변수 할당`이 일어나면, 렉시컬 환경(자료 구조)에 식별자에 해당하는 값을 변경한다. 변수 검색도 이러한 자료 구조 상에서 이뤄진다.



### 스코프 체인에 의한 변수 검색

자바스크립트 엔진은 변수를 참조하는 스코프에서 시작하여 상위 스코프 방향으로 선언된 변수를 검색한다. **절대 하위 스코프로 내려가면서 식별자를 검색하는 일은 없다.**

- 상위 스코프에서 유효한 변수는 하위 스코프에서 참조 가능
- 하위 스코프에서 유효한 변수를 상위 스코프에서 참조 불가능

=&gt; 스코프 체인으로 연결된 계층적 구조는 **상속**과 유사하다.



### 스코프 체인에 의한 함수 검색

함수 선언문으로 함수를 정의하면, **런타임 이전에 함수 객체가 먼저 생성**된다. 이때 자바스크립트 엔진은 함수 이름과 동일한 식별자를 암묵적으로 선언하고 생성된 함수 객체를 할당한다.   
즉, 모든 함수는 함수 이름과 동일한 식별자에 할당된다. 함수가 호출되면, 자바스크립트 엔진은 함수 호출을 위해 함수를 가리키는 **식별자를 먼저 검색**한다.   
이처럼 함수도 식별자에 할당되기 때문에 스코프를 갖는다.

=&gt;  스코프를 변수를 검색할 때 사용하는 규칙이라기보단 **식별자를 검색하는 규칙**이라고 표현하는 편이 조금 더 적합하다.



<details class="orca-details">
<summary>스코프 체인 검색은 성능에 영향을 줄까?</summary>

이론적으로는 그렇다. 스코프 체인이 깊을수록 바깥쪽 변수를 찾기 위해 더 많은 단계를 거쳐야 하므로 검색 비용이 늘어난다. 다만 최신 V8 등의 엔진은 코드를 실행하기 전에 **어떤 변수가 어느 스코프에 있는지 정적으로 분석(컴파일 타임 최적화)** 해두는 경우가 많아서, 실제 체감 성능 차이는 미미한 경우가 대부분이다. 그럼에도 불구하고 "깊은 중첩 함수 + 반복문 안에서의 바깥 변수 참조" 같은 패턴은 가독성 측면에서도 좋지 않으므로, 성능보다는 **코드 복잡도 관리 차원**에서 중첩을 얕게 유지하는 것이 권장된다.

</details>

<details class="orca-details">
<summary>스코프 체인에서 식별자를 못 찾으면 무조건 에러가 날까?</summary>

전역 스코프까지 검색했는데도 식별자를 찾지 못하면 `ReferenceError`가 발생한다. 단, **비 strict 모드에서 선언 없이 값을 할당하는 경우(암묵적 전역, implicit global)**는 예외다.

```javascript
function foo() {
  x = 10; // 선언 없이 할당 → 암묵적으로 전역 변수 생성 (비권장!)
}
foo();
console.log(x); // 10
```

이건 엄밀히는 "식별자 검색에 실패해서 에러가 나는 것"이 아니라, 자바스크립트의 관대한(?ㅋㅋ) 설계 때문에 할당 시점에 전역 스코프에 프로퍼티를 새로 만들어버리는 것이다. `'use strict'`를 사용하면 이 경우에도 `ReferenceError`가 발생하도록 막을 수 있어서, **strict 모드 사용이 권장되는 대표적인 이유** 중 하나다.

</details>



## 함수 레벨 스코프

- C나 자바 등을 비롯한 대부분의 프로그래밍 언어는 함수 몸체 뿐만 아니라 모든 코드 블록이 지역 스코프를 만든다. =&gt; 지역 레벨 스코프 
- `var` 키워드로 선언된 변수는 오로지 함수의 코드 블록(함수 몸체)만을 지역 스코프로 인정한다. =&gt; 함수 레벨 스코프



```javascript
var i = 10;

for (var i = 0; i<5; i ++) {
  console.log(i); // 0 1 2 3 4
}

console.log(i); //5
```

만약  레벨 스코프라면, for문에서 선언된 i 변수가 for문의 코드 블록 내에서만 유효한 지역 변수이다. 하지만 var 키워드로 선언된 변수는 블록 레벨 스코프를 인정하지 않기 때문에 i는 전역 변수가 된다.   
=&gt; 전역 변수 i는 중복 선언되고 그 결과 의도치 않은 전역 변수의 값이 재할당된다.



<details class="orca-details">
<summary>그러면 왜 var은 이렇게 설계되었을까?</summary>

자바스크립트는 1995년 브렌던 아이크가 단 10일 만에 처음 설계했고, 당시 C언어 등 기존 언어의 관습과 웹 스크립팅의 간단한 요구사항을 절충하며 빠르게 만들어졌다. 함수 레벨 스코프만 지원한 것은 설계 당시 "간단한 문서 조작 스크립트"를 염두에 뒤 놓은 결과로 보는 시각이 많다. 이후 프로그램이 대형화되면서 블록 레벨 스코프의 필요성이 커졌고, 이를 해결하기 위해 ES6에서 `let`, `const`가 도입된 것이다. 즉 `var`가 "잘못된 것"이라기보다는, **시대의 요구사항이 달라지며 더 나은 대안이 추가된 것**으로 이해하는 것이 정확하다.

</details>

<details class="orca-details" open>
<summary>`try...catch`의 `catch` 블록도 자신만의 스코프를 가질까?</summary>

가진다. `catch (e) { ... }`에서 `e`는 `catch` 블록 `{}` 내부에서만 유효한 **독립적인 블록 스코프 변수**이다. `let`, `const`로 선언한 변수와 동일하게 취급된다고 보면 된다.

```javascript
try {
  throw new Error('에러 발생');
} catch (e) {
  console.log(e.message); // '에러 발생'
}
console.log(e); // ReferenceError: e is not defined
```

`catch` 블록 안에서는 `e.message`가 정상적으로 출력되지만, 블록을 벗어난 `console.log(e)`는 `e`라는 식별자를 찾지 못해 `ReferenceError`를 던진다.

<details class="orca-details">
<summary>왜 하필 `catch`의 매개변수만 이렇게 블록 스코프로 만들었을까? 함수 매개변수처럼 취급하면 안 됐나?</summary>

`try...catch`는 "예외가 발생했을 때만 잠깐 필요한 정보(에러 객체)"를 다루는 구문이다. 이 에러 객체를 함수 매개변수처럼 넓은 범위(함수 레벨)에 남겨두면, `catch` 블록을 벗어난 뒤에도 `e`라는 이름이 계속 유효 범위에 남아 다른 변수와 충돌하거나, 예외 처리가 끝났는데도 옛 에러 정보가 스코프에 남아 혼란을 줄 수 있다. "에러 처리라는 목적이 끝나면 그 정보도 함께 사라지는 것"이 자연스럽기 때문에, 명세 자체에서 `catch` 절의 매개변수를 독립적인 블록 스코프로 규정한 것이다.

</details>

</details>



## 렉시컬 스코프

```js
var x = 1;

function foo(){
  var x = 10;
  bar();
}

function bar(){
  console.log(x);
}

foo();
bar();
```

위 코드의 실행 결과는 어떻게 나올까? 실행 결과는 `bar` 함수의 상위 스코프가 무엇인지에 따라 결정된다. 



**함수를 어디서 호출했는지에 따라 함수의 상위 스코프를 결정하면(동적 스코프)**

bar 함수의 상위 스코프는 foo 함수의 지역 스코프와 전역 스코프일 것이다.

함수를 정의하는 시점에는, 함수가 어디서 호출될지 알 수 없다. 따라서 함수가 호출되는 시점에 동적으로 상위 스코프를 결정해야 하기 때문에 동적 스코프라고 부른다.



**함수를 어디서 정의했는지에 따라 함수의 상위 스코프를 결정한다면(렉시컬 스코프)**

bar 함수의 상위 스코프는 전역 스코프일 것이다. 

함수 정의가 평가되는 시점에 상위 스코프가 정적으로 결정되기 땜누에 정적 스코프 또는 렉시컬 스고프라고 부른다.  
=&gt; 함수가 호출된 위치는 상위 스코프의 결정에 어떠한 영향도 주지 않는다. 함수의 상위 스코프는 언제나 자신이 정의된 스코프다. **함수의 상위 스코프는 언제나 자신이 정의된 스코프다.**



> 함수 정의가 실행되어 생성된 함수 객체는 이렇게 결정된 상위 스코프를 기억한다. 함수가 호출될 때마다 함수의 상위 스코프를 참조할 필요가 있기 때문이다.



때문에 위 예제에서는 `bar` 함수는 렉시커러 스코프에 따라 **전역에서 정의된 함수**다. 함수 선언문으로 정의되었기 때문에 코드가 실행되기 전에 먼저 평가되어 함수 객체를 생성한다. 생성된 함수 객체는 자신이 정의된 **전역 스코프를 기억**한다. 

전역 스코프를 기억한 `bar`함수를 호출하면, 어디인지 관계없이 **전역 스코프를 상위 스코프로 사용**한다. 즉, 위 예제에서는 1을 두 번 출력한다. 



<details class="orca-details">
<summary>렉시컬 스코프가 클로저와 어떤 관계가 있을까?</summary>

클로저는 "함수가 자신이 정의된 렉시컬 스코프를 기억한다"는 성질을 이용하는 개념이다. 즉 렉시컬 스코프는 클로저가 성립하기 위한 **전제 조건**입니다. 함수가 호출 시점이 아니라 정의 시점의 스코프를 기억하기 때문에, 함수가 자신이 정의된 환경을 벗어나 다른 곳에서 호출되어도(심지어 원래 스코프를 만든 외부 함수가 이미 종료되었어도) 그 환경의 변수에 계속 접근할 수 있는 것이다.

</details>

| 중복 선언      | 허용 (덮어씀)            | 불가 (SyntaxError)  | 불가 (SyntaxError)  |
| 재할당        | 가능                  | 가능                | 불가능               |
| 호이스팅 시 초기화 | `undefined`로 즉시 초기화 | 초기화하지 않음 (TDZ 발생) | 초기화하지 않음 (TDZ 발생) |
| 전역 선언 시    | `window`의 프로퍼티가 됨   | `window`의 프로퍼티 아님 | `window`의 프로퍼티 아님 |




### 일시적 사각지대 (TDZ, Temporal Dead Zone)

`let`, `const`도 `var`와 마찬가지로 호이스팅이 일어나긴 하지만, **선언 단계와 초기화 단계가 분리**되어 있다. 스코프 진입 시 변수가 등록되긴 하지만 초기화되지 않은 상태로 남아있다가, 실제 `let`/`const` 선언문이 실행되는 순간 비로소 초기화된다. 선언은 되었지만 초기화되지 않은 이 구간을 **일시적 사각지대(TDZ)** 라고 부른다.



<details class="orca-details">
<summary>&quot;let은 호이스팅이 안 된다&quot;는 말을 자주 듣는데, 방금 설명과 모순 아닌가?</summary>

정확히는 `let`**,** `const`**도 호이스팅이 일어나지만,** `var`**처럼** `undefined`**로 즉시 초기화되지 않을 뿐**이다. 만약 진짜로 호이스팅이 전혀 일어나지 않는다면, 아래 코드는 `ReferenceError`가 아니라 전역 스코프의 `a`(있다면)를 참조하거나 별개의 동작을 했을 것이다.

javascript

```javascript
let a = 1;
{
  console.log(a); // ReferenceError (전역의 a=1이 출력되지 않음!)
  let a = 2;
}
```

만약 블록 내부의 `let a`가 호이스팅되지 않았다면, `console.log(a)`는 스코프 체인을 타고 올라가 전역의 `a`(값 1)를 출력했어야 한다. 하지만 실제로는 `ReferenceError`가 발생한다. 이는 블록 스코프 안에 `let a`가 이미 "선언"되어 있고(호이스팅이 일어난 증거), 다만 아직 "초기화"되지 않아 TDZ에 걸려있기 때문이다. 즉 정확한 표현은 "let은 호이스팅되지만, 초기화 전까지는 접근할 수 없다"이다.

</details>

<details class="orca-details">
<summary>TDZ는 왜 도입되었나? 그냥 var처럼 undefined로 초기화하면 안 됐나?</summary>

TDZ는 의도적인 설계이다. "변수를 선언하기 전에 사용하는 것"은 대부분의 경우 프로그래머의 실수이거나 코드 순서에 대한 오해에서 비롯된다. `var`처럼 조용히 `undefined`를 반환해버리면 이런 실수가 에러 없이 넘어가서 나중에 엉뚱한 곳에서 버그로 발현된다. TDZ는 이런 실수를 **선언 이전 접근 시점에 즉시, 명확하게** 잡아내기 위한 안전장치다. "빠르게 실패하라(fail fast)"는 원칙이 언어 설계에 반영된 사례라고 볼 수 있다.

</details>


# 14장. 전역 변수의 문제점

## 변수의 생명 주기

### 지역 변수의 생명 주기

변수는 선언 -&gt; 할당 -&gt; 소멸의 3가지 단계를 거친다. 
만약 변수에 생명 주기가 없다면, 한 번 선언된 변수는 프로그램을 종료하지 않는 한 영원히 메모리 공간을 점유하게 될 것이다.



**지역 변수 선언의 실행 시점과 변수 호이스팅**

변수 선언은 선언문이 어디 있듯이 상관없이 런타임 이전에 가장 먼저 실행된다..... 라고 저번에 배웠지만 이건 전역 변수에 한정되는 설명이다. 그렇다면 지역 변수는 어느 시점에 실행될까?



함수 내부에서 선언한 **지역 변수**는, 함수가 호출된 직후 **함수 몸체 내 코드가 순차적으로 실행되기 이전에** 자바스크립트 엔진에 의해 먼저 실행된다. 



```js
var x = 'global';

function foo(){
  
  console.log(x); // 1️⃣ ??
  var x = 'local';
  console.log(x); // local
  
  return x;
}

console.log(x); // global
```

위 예제의 foo 함수를 호출하면 함수 몸체의 다른 문들이 실행되기 이전에 x 변수의 선언문이 자바스크립트 엔진에 의해 가장 먼저 실행되어 **x 변수 선언 및 undefined로 초기화된다.**  
그 후, 함수 몸체를 구성하는 문들이 순차적으로 실행되기 시작하고, 변수 할당문이 실행되면 x 변수에 값이 할당된다.   
이후 함수가 종료되면 x 변수도 소멸되어 생명 주기가 종료된다.  
=&gt; 함수 내부에서 선언된 지역 변수는 **함수가 호출되어 실행되는 동안에만 유효**하다. 즉, **지역 변수의 생명 주기는 함수의 생명 주기와 일치**한다.



지역 변수는 함수 몸체 내부에서 선언되고, 그 함수가 호출될 때 새로운 스코프(정확히는 렉시컬 환경)가 만들어지면서 그 변수도 함께 만들어진다. 함수 호출이 끝나면 이 스코프에 대한 참조가 더 이상 남아있지 않으므로, 자바스크립트 엔진의 **가비지 컬렉터**가 이를 메모리에서 회수할 수 있게 된다.



**지역 변수가 함수보다 오래 생존하는 경우**

함수 몸체 내부에서 선언된 **지역 변수**는 **함수의 생명 주기**와 대부분 일치하지만, 지역 변수가 함수보다 오래 생존하는 경우도 있다.



- 변수 :  하나의 값을 저장하기 위해 **메모리 공간 자체**, 또는 메모리 공간을 **식별하기 위해 붙인 이름**
- 변수 생명 주기 : 메모리 공간이 확보된 시점부터 메모리 공간이 해제되어 가용 메모리 풀에 반환되는 시점



함수 내부 **지역 변수**는 함수가 생성된 **스코프**에 등록된다. 따라서, 변수는 자신이 등록된 **스코프가 소멸(메모리 해제)**될 때까지 유효하다. 할당된 메모리 공간은 더 이상 그 누구도 참조하지 않을 때 가비지 콜렉터에 의해 해제되어 가용 메모리 풀에 반횐된다.  
=&gt; 메모리 공간을 참조하고 있으면, 해제되지 않고 확보된 상태로 남아있게 되는 것

스코프도 마찬가지로, 누군가 스코프를 참조하고 있으면 스코프는 소멸하지 않고 생존하게 된다.



<details class="orca-details">
<summary>함수 실행이 끝나면 지역 변수가 소멸한다&quot;고 했는데, 클로저는 왜 예외일까?</summary>

확히 말하면 지역 변수가 "소멸하는 것이 원칙"이지만, **가비지 컬렉션은 '더 이상 참조되지 않을 때' 일어나는 것**이지 '함수 실행이 끝나는 순간 무조건 일어나는 것'이 아니다. 만약 함수 내부에서 정의된 중첩 함수가 외부로 반환되거나 어딘가에 저장되어 계속 살아있다면, 그 중첩 함수가 상위 스코프(외부 함수의 지역 변수들)를 계속 참조하고 있으므로 가비지 컬렉터는 이를 회수하지 않는다. 이것이 바로 클로저가 동작하는 원리이다.

javascript

```javascript
function makeCounter() {
  let count = 0; // makeCounter 호출이 끝나도 소멸하지 않음
  return function () {
    return ++count; // 이 함수가 count를 계속 참조하고 있기 때문에
  };
}
const counter = makeCounter();
console.log(counter()); // 1
console.log(counter()); // 2
```

즉 "함수가 끝나면 변수가 사라진다"는 규칙에는 "단, 그 변수를 참조하는 무언가가 외부에 살아있지 않다면"이라는 전제가 숨어 있다.

</details>



**스코프 단위로 동작되는 호이스팅**

```js
var x = 'global';

function foo() {
  console.log(x); // 1️⃣
  var x = 'local';
}

foo();
console.log(x) // global
```

위 예제에서 1️⃣ 시점에는 undefined가 찍힌다.   
지역 변수는 해당 함수의 몸체 내의 문이 순차적으로 실행되기 이전에 선언되고, undefined가 할당된다. 전역 변수 x를 참조하는 것이 아니라 지역 변수 x를 참조해 값을 출력하는 것이다. 즉, 해당 시점에 이미 지역 변수 x는 선언되어 undefined 값을 갖는 것이다.



위 예제에서 **호이스팅은 스코프를 단위로 동작**하는 것을 알 수 있다. 

- 지역 변수의 호이스팅 : 지역 변수의 선언이 지역 스코프의 선두로 끌어 올려진 것처럼 동작 =&gt; 함수 전체에서 유효
- 전역 변수의 호이스팅 : 전역 변수의 선언이 전역 스코프의 선두로 끌어 올려진 것처럼 동작 =&gt; 전역 전체에서 유효



호이스팅은 변수 선언이 스코프의 선두로 끌어 올려진 것처럼 동작하는 자바스크립트 고유의 특징이다.



### 전역 변수의 생명 주기

젼역 변수는 명시적인 호출 없이 실행된다. 즉, 실행을 위한 진입점이 있는 함수와는 다르게 코드가 **로드되자마자 해석되어 실행된다.**

- 함수 종료 : 함수 몸체의 마지막 문 또는 반환문이 실행된 후
- 전역 코드 종료 : 반환문을 사용할 수 없어, 마지막 문이 실행된 후



**var 키워드로 선언한 전역 변수와 전역 객체**

var 키워드로 선언한 전역 변수는 전역 객체의 프로퍼티가 된다. 이는 전역 변수의 생명 주기가 전역 객체의 생명 주기와 일치한다는 것을 말한다. 



> `전역 객체` 코드가 실행되기 이전 단계에, 자스 엔진에 의해 어떤 객체보다도 먼저 생성되는 특수한 객체
>
> - 클라이언트 사이드 환경(브라우저) : window
> - 서버 사이드 환경(node.js): global
> - 전역 객체를 가리키는 식별자 : globalThis (ES11에서 통일됨)
> - 전역 객체의 프로퍼티 : 표준 빌트인 객체, 호스트 객체, var 키워드로 선언한 전역 변수, 전역 함수



브라우저 환경을 기준으로, 전역 객체는 window이므로 var 키워드로 선언한 전역 변수는 전역 객체 window의 프로퍼티이다. 전역 객체 window는 웹페이지를 닫기 전까지 유효하며, var 키워드로 선언한 전역 변수는 웹 페이지를 닫을 때까지 유효하다. 



즉, **var 키워드로 선언한 전역 변수의 생명 주기는 전역 객체의 생명 주기와 일치**한다. 



## 전역 변수의 문제점

### 암묵적 결합

전역 변수는 코드 어디서든 참조하고 할당하기 위해서 사용한다. 이것은 모든 코드가 전역 변수를 참조하고 변경할 수 있는 암묵적 결합을 허용한다는 것과 같다.   
=&gt; 변수의 유효 범위가 클수록 가독성이 떨어지고, 의도치 않게 상태가 변경될 수 있다.



### 긴 생명 주기

- `전역 변수` 생명주기 길다 | 메모리 리소스를 오랜 기간 소비 | 변수를 변경할 시간, 기회가 많음
- `지역 변수` 생명주기 짧음 | 메모리 리소스를 짧은 기간 소비 | 변수를 변경할 시간, 기회가 적음

심지어 var 키워드로 선언한 변수는 변수의 **중복 선언을 허용한다.**  
결국 생명 주기가 긴 전역 변수의 이름이 중복될 가능성이 있고, 의도치 않은 재할당이 발생할 수 있다.



### 스코프 체인 상에서 종점에 존재

전역 변수는 스코프 체인 상에서 종잠에 검색하다. 이는 변수 검색 시, 전역 변수가 가장 마지막에 검색된다는 것을 뜻한다.  
=&gt; 즉, 전역 변수의 검색 속도가 가장 느리다. 



### 네임스페이스 오염

자바스크립트는 파일이 분리되어 있어도 **하나의 전역 스코프를 공유**한다.  
따라서 다른 파일 내 동일한 이름으로 명명된 변수나 전역 함수가 같은 스코프 내에 존재할 경우 예상치 못한 결과를 가져올 수 있다.



<details class="orca-details">
<summary>전역 변수의 생명 주기가 왜 &quot;문제&quot;로 이어지나요? 그냥 오래 살아있는 게 나쁜 건가요?</summary>

"오래 산다는 것" 그 자체보다, **누구나 접근할 수 있는 상태로 오래 산다** 는 것이 문제이다. 암묵적 결합, 긴 생명 주기로 인한 상태 관리 어려움, 스코프 체인 최말단으로 인한 검색 성능, 네임스페이스 오염은 사실 전부 "넓은 접근 범위 + 긴 생명 주기"라는 두 가지 특성의 조합에서 파생된다. 만약 전역 변수가 넓은 범위에서 접근 가능하지만 아주 짧게 살고 사라진다면 문제가 훨씬 줄어들 것이고, 반대로 오래 살지만 극히 제한된 범위에서만 접근 가능하다면(모듈 스코프의 캡슐화된 상태처럼) 이 역시 문제가 훨씬 줄어든다.

</details>



## 전역 변수의 사용을 억제하는 방법

### 즉시 실행 함수

즉시 실행 함수는 함수를 정의하는 동시에 **단 한 번만 호출**된다. 모든 코드를 즉시 실행 함수로 감싸면 모든 변수는 **즉시 실행 함수의 지역 변수**가 된다.  
=&gt; 전역 변수가 생성되지 않아, 라이브러리 등에서 자주 사용된다.



### 네임스페이스 객체

네임스페이스 역할을 담당할 객체를 전역에 생성 후, 전역 변수처럼 사용하고 싶은 **변수를 프로퍼티에 추가**하는 방법이다.  
네임스페이스 객체에 또 다른 네임스페이스 객체를 프로퍼티로 추가하여, 계층적으로 구성하는 것도 가능하다.

식별자 충돌을 방지할 순 있지만, 네임스페이스 객체 자체가 전역 변수에 할당되므로 **그닥 유용하진 않다. ㅠㅠ**

```js
var MYAPP = {}; // 전역 네임스페이스 객체

MYAPP.name = 'sozzang';
console.log(MYAPP.name); // sozzang

MYAPP.person = { // 네임스페이스 객체를 프로퍼티로 추가
  address: 'Seoul'  
}
```



### 모듈 패턴

모듈 패턴은 클로저를 기반으로 동작하기 때문에... 쇽샥 알아보면

모듈 패턴은 클래스를 모방해서 관련 있는 변수와 함수를 모아 즉시 실행 함수로 감싸 하나의 모듈을 만든다. 모듈 패턴을 통해 전역 변수의 억제와 캡슐화까지 구현 가능하다.



**캡슐화**

캡슐화는 객체의 상태를 나타내는 **프로퍼티**와 프로퍼티를 참조하고 있는 **메서드**를 하나로 묶는 것이다. 캡슐화는 객체의 특정 프로퍼티나 메서드를 감출 목적으로 사용하기도 한다.



**정보 은닉**

대부분의 객체 지향 프로그래밍 언어는, 클래스를 구성하는 멤버에 `접근 제한자`(public, private, protected 등)를 사용하여 **공개 범위를 한정**할 수 있다.  
이를 통해, 클래스 외부에는 제한된 접근 권한을 제공하며, 원하지 않은 외부의 접근으로부터 내부를 보호할 수 있다.

- `public` 외부에서 데이터 또는 메서드에 접근이 가능함
- `private` 외부에서 데이터 또는 메서드에 접근이 불가능하고 내부에서만 접근 가능

하지만 `자바스크립트`는 **접근 제한자를 제공하지 않는다.**  
그래서 자바스크립트에서 (한정적이긴 하지만) **정보 은닉을 위해 모듈 패턴을 사용**한다.



### ES6 모듈

ES6 모듈을 사용하면, 전역 변수를 사용할 수 없다  
=&gt; 모듈 내에서 var 키워드로 선언한 변수는 전역 변수도 window 객체의 프로퍼티도 아니다. 



**사용 방법**

script 태그에 `type="module"` 어트리뷰트를 추가한다.  
모듈의 파일 확장자는 `mjs`가 권장된다.

```javascript
<script type="module" src="app.mjs"></script>
```

하지만.... 구형 브라우저에서는 동작히지 않으며 트랜스파일링이나 번들링이 필요하기 때문에 ES6 모듈보다는 Webpack 등의 모듈 번들러를 일반적으로 사용한다.



<details class="orca-details">
<summary>모듈 패턴과 ES6 모듈은 결국 같은 목적인데, 실무에서 모듈 패턴을 지금도 쓸 일이 있을까?</summary>

"파일 단위 모듈화"라는 목적으로는 ES6 모듈이 거의 완전히 대체했다. 다만 **모듈 패턴의 핵심 아이디어인 "클로저를 이용해 비공개 상태를 만드는 기법" 자체는 지금도 매우 널리 쓰인다.**

예를 들어 React의 커스텀 훅에서 `useState`로 감싸지 않은 내부 헬퍼 변수를 클로저로 캡슐화한다거나, 팩토리 함수 패턴으로 객체를 생성할 때 `private` 필드처럼 동작하는 지역 변수를 만드는 경우가 그렇다. 즉 "모듈 패턴"이라는 이름의 사용 빈도는 줄었지만, 그 기반 원리(IIFE + 클로저로 캡슐화)는 다른 이름과 형태로 지금도 곳곳에서 쓰이고 있다.

</details>

<details class="orca-details">
<summary>ES 모듈(import/export)을 쓰면 전역 변수 문제가 완전히 사라지나?</summary>

크게 개선되지만 완전히 사라지는 건 아니다. ES 모듈의 각 파일은 **자신만의 모듈 스코프**를 가지므로, `export`하지 않은 최상위 변수는 자동으로 그 파일 내부에서만 유효한 "사실상의 지역 변수"가 된다. 즉 별도의 IIFE 없이도 자연스럽게 전역 스코프 오염을 방지해준다. 다만 여전히 **진짜 전역 객체(**`window`**,** `globalThis`**)에 직접 값을 붙이는 코드**(예: 서드파티 스크립트 삽입, 레거시 코드와의 상호운용)는 존재할 수 있고, 이런 경우의 오염 문제는 모듈 시스템만으로 해결되지 않는다. 그래서 대규모 프로젝트에서는 여전히 ESLint의 `no-undef`, `no-global-assign` 같은 규칙을 함께 사용해 전역 오염을 감시한다.

</details>

<details class="orca-details">
<summary>전역 변수를 꼭 써야 하는 상황은 무슨 상황이 있을까?</summary>

예를 들어 애플리케이션 전체에서 공유해야 하는 설정값, 다국어 리소스, 혹은 브라우저 API가 제공하는 전역 객체(`window`, `document`) 자체가 그렇다. 다만 이런 경우에도 "네이키드 전역 변수"를 여러 개 흩뿌리기보다는, **하나의 네임스페이스 객체나 모듈로 응집시켜 export하는 패턴**을 사용하는 것이 일반적이다. 최근에는 React의 Context API, 상태 관리 라이브러리(Redux, Zustand, Jotai 등)가 "전역적으로 공유되지만 스코프가 통제된 상태"를 제공하는 방식으로 이 문제를 구조적으로 해결하고 있다.

</details>
