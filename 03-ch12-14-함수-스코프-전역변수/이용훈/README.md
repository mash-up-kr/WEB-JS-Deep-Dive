# 모던 자바스크립트 Deep Dive — 13장 스코프 / 14장 전역 변수의 문제점

## 13장. 스코프

### 스코프란

모든 식별자(변수 이름, 함수 이름 등)는 자신이 선언된 위치에 의해 유효 범위, 즉 다른 코드가 자신을 참조할 수 있는 범위가 결정된다. 스코프는 자바스크립트 엔진이 식별자를 검색할 때 사용하는 규칙이다.

자바스크립트는 `var`, `let`, `const` 선언 방식에 따라 스코프가 다르게 동작한다는 점도 기억해둘 것.

```js
var x = 'global';

function foo() {
  var x = 'local';
  console.log(x); // local
}

foo();
console.log(x); // global
```

같은 이름 `x`지만 스코프가 다르면 서로 다른 변수다.

### 렉시컬 환경과 실행 컨텍스트

코드가 어디서 실행되며 주변에 어떤 코드가 있는지를 렉시컬 환경이라고 한다. 즉 코드의 문맥은 렉시컬 환경으로 이뤄진다. 이를 구현한 것이 실행 컨텍스트이고, 모든 코드는 실행 컨텍스트에 의해 평가되고 실행된다.

### 스코프는 네임스페이스다

스코프 덕분에 같은 이름의 변수를 충돌 없이 사용할 수 있다. 스코프가 곧 네임스페이스 역할을 하는 것.

### 전역 스코프 vs 지역 스코프

- 전역에서 선언된 변수는 전역 스코프. 어디서든 참조 가능.
- 지역(함수 내부)에서 선언된 변수는 지역 스코프.
- 주의할 점: `var` 기준으로 지역 스코프는 코드 블록이 아닌 **함수에 의해서만** 생성된다. (함수 레벨 스코프)

결국 변수는 선언된 위치에 따라 특성이 달라진다.

### 스코프 체인

전역 스코프 → 외부 함수 스코프 → 내부 함수 스코프처럼 계층적으로 연결된 구조를 스코프 체인이라고 한다.

엔진은 변수를 참조하는 코드의 스코프에서 시작해서 상위 스코프 방향으로 이동하며 변수를 검색한다. 그래서 상위 스코프의 변수를 하위 스코프에서 참조할 수 있고, 반대로 하위 스코프의 변수를 상위에서 참조하는 건 불가능하다. 검색이 위로만 올라가기 때문.

**새로 알게 된 부분**: 스코프 체인이 개념적인 게 아니라 물리적인 실체라는 것. 엔진은 코드 실행 전에 렉시컬 환경이라는 자료구조를 실제로 생성한다.

- 변수 선언이 실행되면 → 식별자가 이 자료구조에 키로 등록됨
- 변수 할당이 일어나면 → 해당 키의 값이 변경됨
- 변수 검색도 이 자료구조 위에서 이뤄짐

렉시컬 환경이 자료구조라는 걸 이번에 처음 알았다.

### 렉시컬 스코프 — 정의가 스코프를 결정한다

```js
var x = 1;

function foo() {
  var x = 10;
  bar();
}

function bar() {
  console.log(x);
}

foo(); // ?
bar(); // ?
```

처음에 예측할 때 좀 헷갈렸는데, 정답은 둘 다 `1`.

`bar`의 상위 스코프는 `bar`가 어디서 **호출**됐는지가 아니라 어디서 **정의**됐는지(전역)로 결정되기 때문이다. 자바스크립트는 렉시컬 스코프(정적 스코프)를 따른다.

"호출이 아닌 정의에 의해 상위 스코프가 결정된다" — 알고 있던 내용인데도 실제 문제로 만나니까 헷갈렸다. 놓치기 쉬운 부분인 듯.

## 14장. 전역 변수의 문제점

### 변수 선언은 런타임 이전에 먼저 실행된다

변수 선언은 코드를 순차적으로 읽으면서 런타임에 실행되는 게 아니라, 런타임 이전 단계에서 엔진에 의해 먼저 실행된다. 이 부분 생각보다 많이 놓치는 듯.

함수 내부의 지역 변수도 마찬가지다. 함수가 호출되면 함수 몸체 코드가 실행되기에 앞서 지역 변수 선언이 먼저 처리된다. 이게 호이스팅.

### 변수의 생명 주기

지역 변수의 생명 주기는 대부분 함수의 생명 주기와 일치한다. 그런데 지역 변수가 함수보다 오래 생존하는 경우도 있다.

변수는 결국 메모리 공간을 식별하기 위해 붙인 이름이라, 메모리가 해제되지 않으면 계속 남아 있다. 함수가 종료돼도 누군가 그 스코프의 변수를 참조하고 있으면 유지되는 것. (나중에 나올 클로저의 토대가 되는 얘기인 듯)

메모리는 그 누구도 참조하지 않을 때 가비지 컬렉터(GC)에 의해 해제된다.

**궁금했던 것: "그 누구도 참조하지 않는다"는 걸 GC는 어떻게 알까?**

찾아보니 참조를 하나하나 세는 방식이 아니라 도달 가능성(reachability)으로 판단한다. 루트(전역 객체, 현재 실행 중인 함수의 지역 변수 등)에서 출발해 참조를 따라가며 닿을 수 있는 객체를 전부 표시하고(mark), 닿지 못한 나머지를 해제한다(sweep). 이게 mark-and-sweep 방식. 그래서 A와 B가 서로 참조하는 순환 참조여도 루트에서 못 닿으면 수거된다.

그리고 역설적으로 이게 전역 변수의 "긴 생명 주기" 문제의 정체이기도 하다. 전역 객체는 루트 그 자체라서, 전역에 매달린 값은 페이지가 살아 있는 한 절대 도달 불가능 상태가 되지 않는다. 즉 GC가 영원히 수거하지 못한다.

### 전역 변수의 문제점

- **암묵적 결합**: 어디서든 읽고 쓸 수 있어서, 값이 어디서 바뀌는지 코드만 봐서는 추적이 안 된다.
- **긴 생명 주기**: 앱이 살아 있는 동안 계속 메모리를 점유하고, 상태가 오염될 기회도 그만큼 길어진다.
- **네임스페이스 오염**: 파일이 달라도 전역 스코프는 하나라서, 같은 이름을 선언하면 에러 없이 조용히 덮어쓴다.
- **스코프 체인 종점**: 전역 변수는 스코프 체인의 가장 마지막에 검색되므로 검색 속도가 가장 느리다. (이건 처음 알았다)

앞의 세 개는 사실 뻔한 얘기인데, 스코프 체인 종점에 있어서 검색이 가장 느리다는 건 이번에 처음 알게 된 관점이었다.

### 결론

책의 결론: "전역 변수를 반드시 사용해야 할 이유를 찾지 못한다면 지역 변수를 사용하라." 변수의 스코프는 좁을수록 좋다.

여기서 든 의문 — 나는 지금까지 전역 변수를 무조건 금지하는 느낌으로 개발해왔는데, 결국 "사용해야 할 이유"가 있으면 써도 된다는 건가? 그런 이유가 실제로 있긴 할까?

→ 있다. 우리 회사 프로젝트가 정확히 그 케이스다. 아래에 정리.

## 실무 연결 — 우리 프로젝트에서 전역 변수는 왜/어떻게 쓰이는가

우리 프로젝트는 번들러도 모듈 시스템(ESM `import`)도 없는 서버 렌더링 기반 멀티페이지 앱이다. JS 파일들은 페이지에 `<script src>` 태그로 나열되어 로드된다. 이 구조에서는 책이 말한 "반드시 사용해야 할 이유"가 구조적으로 존재한다.

### 전역을 써야만 하는 이유

1. **모듈 시스템 부재** — `import`/`export`가 없으니, 파일 A의 값을 파일 B가 쓰는 유일한 통로가 전역 스코프다.
2. **서버 → 브라우저 데이터 전달** — 서버가 렌더링 시점에 아는 값(주문 정보, 국가/언어, 각종 설정)을 JS로 넘기는 표준 수단이 인라인 스크립트의 전역 변수다.
3. **서드파티 SDK의 계약** — 분석/광고 SDK들이 특정 전역 이름을 요구한다. 이건 선택권 자체가 없다.
4. **레거시 인라인 핸들러** — 마크업의 `onclick="fnXxx()"`가 호출하는 함수는 전역이어야 찾을 수 있다.

정리하면, "전역 금지"는 모듈 시스템이 있는 환경의 규칙이고, 우리 환경에서는 "전역을 최소화하고 정리해서 쓰는" 규칙으로 바뀐다.

### 책의 문제점이 실제로 나타나는 모습

- **암묵적 결합**: 서버가 주입한 전역 설정 객체를 수십 개 파일이 읽고 있다. 값이 어디서 바뀌는지 한눈에 안 보인다.
- **네임스페이스 오염**: 네임스페이스 밖에 풀려 있는 최상위 `var`가 상당히 많다. 다른 파일이나 페이지 인라인 스크립트가 같은 이름을 선언하면 에러 없이 조용히 덮어쓴다. 실무에서 제일 무서운 부분.
- **긴 생명 주기**: 멀티페이지 앱이라 페이지 이동 시 전역이 리셋되는 게 그나마 다행. SPA였으면 누수가 훨씬 심각했을 것.

### 억제 패턴 1 — 네임스페이스 객체

여러 파일이 공유해야 하는 함수나 상태를 노출할 때 쓴다. 전역에 이름을 딱 하나만 만들고 나머지는 전부 그 아래에 매달아서 충돌 가능 면적을 최소화하는 방식.

```js
// 공통 스크립트의 관례적인 첫 줄
window.app = window.app || {}; // 있으면 재사용, 없으면 생성

app.global = { /* 서버 주입 설정 */ };
app.cookie = { /* 쿠키 유틸 */ };
```

핵심은 "있으면 재사용, 없으면 생성" 패턴 덕분에 로드 순서와 상관없이 어느 파일이 먼저 실행돼도 안전하게 하나의 네임스페이스에 합류한다는 점.

### 억제 패턴 2 — 즉시 실행 함수(IIFE)로 구현 은닉

파일 내부에서만 쓰는 변수나 헬퍼가 있을 때 쓴다. 사실상 모든 파일이 이 패턴이다.

최상위에 `var`를 쓰면 전부 전역이 되어버리니까, 함수 스코프로 감싸서 "파일 = 하나의 스코프"를 흉내 내는 것. 모듈 시스템이 없는 환경에서 모듈을 흉내 내는 유일한 방법이다.

```js
(function () {
  var onlyOnce = 1;      // 전역이 아니다. 이 IIFE 안에서만 보인다.
  var internalList = [];

  // 공개할 것만 네임스페이스에 붙인다
  window.app.doSomething = function () { /* ... */ };
})();
```

### 억제 패턴 3 — 모듈 패턴 (IIFE + 네임스페이스)

비공개 상수나 헬퍼는 숨기고 정해진 공개 API만 외부에 제공하고 싶을 때 쓴다. 클로저로 내부 구현을 은닉하고, 네임스페이스에 노출한 객체만 공개 인터페이스가 되는 구조.

```js
(function () {
  var PRIVATE_CONST = ['a', 'b'];    // 비공개 상수
  function privateHelper() { /* */ } // 비공개 헬퍼

  window.app.someFeature = {  // 공개 API. 이것만 밖에서 보인다.
    run: function () { return privateHelper(PRIVATE_CONST); }
  };
})();
```

여기서 14장 이론이 그대로 등장한다. "지역 변수가 함수보다 오래 생존하는 경우"가 바로 이 패턴이다. IIFE는 이미 실행이 끝났지만, `PRIVATE_CONST`는 공개 API의 메서드들이 클로저로 참조하고 있는 한 계속 살아 있다. 책에서 신기하다고 넘어갔던 이론이 실무 패턴의 토대였던 것.

### 실무 결론 — 전역 사용 판단 기준

- 파일 간 공유, 서버 데이터 주입, SDK 계약 → 써야 한다. 단, 네임스페이스 객체 아래에만.
- 파일 안에서만 쓰는 값 → 무조건 IIFE 안에. 최상위 `var`는 "이유 있는 전역"이 아니라 그냥 사고 대기 상태다.
- 판단 기준은 결국 하나다. "이 값을 다른 파일이 읽어야 하는가?" 아니면 지역(IIFE 내부), 맞으면 네임스페이스.

책의 결론인 "변수의 스코프는 좁을수록 좋다"는 이 환경에서도 그대로 유효하다. 다만 그게 "전역 0개"가 아니라 "의도된 전역 1개 + 나머지 전부 은닉"으로 실현될 뿐이다.
