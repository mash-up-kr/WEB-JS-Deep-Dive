## 20장 strict mode

### 암묵적 전역

```jsx
function foo() {
  x = 10;
}
foo();

console.log(x); // 10
```

- `x`는 어디서도 선언되지 않았으니 ReferenceError가 날 것 같지만, 엔진이 **전역 객체에 x 프로퍼티를 동적으로 생성**해 버림 → **암묵적 전역**
- 버그의 원인이 되기 쉬우므로 변수는 반드시 선언한 후에 사용하는 게 좋음
- 그래도 실수는 생기기 마련이라 ES5부터 **strict mode** 도입
    - 문법을 더 엄격하게 적용해서, 오류 가능성이 높은 코드나 엔진 최적화를 방해하는 코드에 명시적으로 에러를 발생시킴
- ESLint 같은 린트 도구도 비슷한 효과를 내고, 코딩 컨벤션까지 설정 파일로 강제할 수 있어서 더 유용한 경우가 많음

### 적용 방법

- 전역의 선두나 함수 몸체의 선두에 `'use strict';` 추가
- **선두에 두지 않으면 동작하지 않음**
- 전역에 적용하는 건 피할 것
    - 스크립트 단위로 적용되기 때문에 strict / non-strict 스크립트를 섞으면 오류 가능성이 생김
    - 서드파티 라이브러리가 non-strict일 수도 있음
    - 필요하면 **즉시 실행 함수로 스크립트 전체를 감싸고** 그 선두에 적용
- 함수 단위로 적용하는 것도 피할 것
    - 어떤 함수는 적용하고 어떤 함수는 안 하는 건 바람직하지 않음
    - strict 함수가 참조하는 외부 컨텍스트가 non-strict면 문제가 될 수 있음

### strict mode가 발생시키는 에러

- 암묵적 전역 → **ReferenceError**
- 변수, 함수, 매개변수 `delete` → **SyntaxError**
- 매개변수 이름 중복 → **SyntaxError**
- `with` 문 사용 → **SyntaxError**

### strict mode 적용에 의한 변화

- 함수를 일반 함수로 호출하면 `this`에 `undefined`가 바인딩됨 (일반 함수 안에서는 this를 쓸 일이 없기 때문)
- 매개변수에 전달된 인수를 재할당해도 `arguments` 객체에 반영되지 않음

## 21장 빌트인 객체

### 객체 분류

- **표준 빌트인 객체**: ECMAScript 사양에 정의된, 애플리케이션 전역의 공통 기능을 제공하는 객체. 실행 환경과 관계없이 별도 선언 없이 언제나 사용 가능
- **호스트 객체**: ECMAScript 사양에는 없고 실행 환경이 추가로 제공하는 객체 (브라우저의 DOM, fetch, setTimeout 등 / Node.js 고유 API)
- **사용자 정의 객체**: 사용자가 직접 정의한 객체

### 표준 빌트인 객체

- Object, String, Number, Boolean, Symbol, Date, Math, RegExp, Array, Map, Set, Function, Promise, Reflect, Proxy, JSON, Error 등 40여 개
- **Math, Reflect, JSON을 제외하면 전부 생성자 함수 객체**
    - 프로토타입 메서드 + 정적 메서드 제공
    - Math, Reflect, JSON은 정적 메서드만 제공
- 생성자 함수인 표준 빌트인 객체가 만든 인스턴스의 프로토타입은 그 생성자 함수의 `prototype` 프로퍼티에 바인딩된 객체
    - ex) `new String('a')`의 프로토타입은 `String.prototype`

### 원시값과 래퍼 객체

```jsx
const str = 'hello';

console.log(str.length);        // 5
console.log(str.toUpperCase()); // HELLO
```

- 원시값은 객체가 아니라서 프로퍼티나 메서드를 가질 수 없는데 객체처럼 동작함
- 문자열, 숫자, 불리언에 마침표 표기법으로 접근하면 엔진이 **일시적으로 연관된 객체로 변환**해 줌 → 이 임시 객체가 **래퍼 객체**
- 흐름
    1. 원시값에 접근 → 래퍼 객체 생성 (원시값은 내부 슬롯에 보관, ex. `[[StringData]]`)
    2. 래퍼 객체의 프로토타입 메서드를 상속받아 사용
    3. 처리가 끝나면 다시 원시값으로 돌아가고 래퍼 객체는 GC 대상
- Symbol도 래퍼 객체가 생성됨
- `null`, `undefined`는 래퍼 객체가 없음 → 프로퍼티 접근이나 메서드 호출 시 에러
- 그래서 `new String()`, `new Number()`, `new Boolean()`으로 굳이 래퍼 객체를 만들 필요가 없고 권장하지도 않음

### 전역 객체

- 코드가 실행되기 전에 엔진이 **가장 먼저 생성하는 특수한 객체**, 어떤 객체에도 속하지 않은 최상위 객체
- 브라우저는 `window`(또는 `self`, `this`, `frames`), Node.js는 `global`
- ES11부터 환경 상관없이 `globalThis`로 통일
- 특징
    - 개발자가 의도적으로 생성할 수 없음
    - 프로퍼티 참조 시 `window.`를 생략할 수 있음
    - 표준 빌트인 객체 + 호스트 객체를 프로퍼티로 가짐
    - `var` 전역 변수, 전역 함수는 전역 객체의 프로퍼티가 됨
    - **`let`, `const` 전역 변수는 전역 객체의 프로퍼티가 아님** (보이지 않는 개념적 블록 안에 존재)
    - 브라우저에서는 여러 script 태그로 분리해도 하나의 전역 객체 `window`를 공유

#### 빌트인 전역 프로퍼티

- `Infinity`, `NaN`, `undefined`

#### 빌트인 전역 함수

- `eval`: 문자열을 코드로 실행. 기존 스코프를 런타임에 동적으로 수정할 수 있고, 보안에 취약하고, 최적화가 안 돼서 **사용 금지**
- `isFinite`, `isNaN`
- `parseFloat`, `parseInt`
- `encodeURI` / `decodeURI`: URI 전체를 이스케이프 처리 / 복원
- `encodeURIComponent` / `decodeURIComponent`: URI 구성 요소(쿼리 스트링 등)를 이스케이프 처리 / 복원 (`=`, `?`, `&`까지 인코딩)

#### 암묵적 전역 다시 보기

- 선언 없이 할당한 식별자는 **변수가 아니라 전역 객체의 프로퍼티**
- 그래서 변수 호이스팅이 발생하지 않음
- `delete`로 삭제 가능 (var 전역 변수는 삭제 불가)

## 22장 this

### this란

- 자신이 속한 객체 또는 자신이 생성할 인스턴스를 가리키는 **자기 참조 변수**
- 필요한 이유
    - 객체 리터럴 메서드는 객체 이름으로 재귀 참조할 수 있지만 바람직하지 않음
    - 생성자 함수는 인스턴스를 만들기 전에 정의되니까, 자신이 만들 인스턴스를 가리킬 식별자를 알 수 없음
- this는 엔진이 암묵적으로 생성하고, 코드 어디서든 참조 가능
- 함수를 호출하면 `arguments` 객체와 `this`가 암묵적으로 함수 내부에 전달됨
- 함수 내부에서 this를 지역 변수처럼 사용 가능
- **this 바인딩**: this와 this가 가리킬 객체를 연결하는 것

### 함수 호출 방식과 this 바인딩

- **this 바인딩은 함수 호출 방식에 의해 동적으로 결정됨**
- 비교: 렉시컬 스코프(상위 스코프)는 **함수 정의가 평가되는 시점**에 결정, this는 **호출 시점**에 결정

#### 1. 일반 함수 호출

- this는 전역 객체 (strict mode에서는 `undefined`)
- 메서드 내에서 정의한 **중첩 함수**도 일반 함수로 호출되면 전역 객체
- **콜백 함수**도 일반 함수로 호출되면 전역 객체
- 메서드의 this와 중첩/콜백 함수의 this를 일치시키는 방법
    - `const that = this;`로 담아서 사용
    - `apply` / `call` / `bind`로 명시적 바인딩
    - 화살표 함수 사용 (화살표 함수의 this는 상위 스코프의 this)

#### 2. 메서드 호출

- this는 **메서드를 호출한 객체** (마침표 앞의 객체)
- 메서드는 객체에 포함된 게 아니라 **독립적인 함수 객체**이고, 프로퍼티가 그 함수를 참조하고 있을 뿐
    - 그래서 다른 객체의 프로퍼티에 할당하거나 변수에 할당해서 일반 함수로 호출할 수도 있음 → 이때 this가 바뀜
- 프로토타입 메서드 내부의 this도 해당 메서드를 호출한 객체

```jsx
const person = {
  name: 'Lee',
  getName() { return this.name; }
};

console.log(person.getName()); // Lee

const getName = person.getName;
console.log(getName()); // '' (window.name) → 일반 함수 호출
```

#### 3. 생성자 함수 호출

- this는 **생성자 함수가 (미래에) 생성할 인스턴스**
- `new` 없이 호출하면 일반 함수 호출이 됨

#### 4. apply / call / bind 간접 호출

- `Function.prototype`의 메서드라 모든 함수가 상속받아 사용 가능
- `apply(thisArg, [인수 배열])`: 함수를 **호출**
- `call(thisArg, 인수1, 인수2, ...)`: 함수를 **호출**, 인수를 쉼표로 전달
- `bind(thisArg)`: 함수를 호출하지 않고 **this가 바인딩된 새 함수를 반환**
    - 메서드의 this와 내부 중첩/콜백 함수의 this 불일치를 해결할 때 유용
- apply/call의 대표적인 용도: `arguments` 같은 유사 배열 객체에 배열 메서드 사용

```jsx
function convertArgsToArray() {
  return Array.prototype.slice.call(arguments);
}
```

#### 정리

| 호출 방식 | this |
| --- | --- |
| 일반 함수 호출 | 전역 객체 (strict: undefined) |
| 메서드 호출 | 메서드를 호출한 객체 |
| 생성자 함수 호출 | 생성할 인스턴스 |
| apply/call/bind | 첫 번째 인수로 전달한 객체 |

## 23장 실행 컨텍스트

- 자바스크립트의 동작 원리를 담고 있는 핵심 개념
- 스코프, 호이스팅, 클로저, 이벤트 루프 등을 이해하는 기반

### 소스코드의 타입

- 소스코드는 4가지 타입으로 구분되고, 각각 실행 컨텍스트를 생성함
- 구분하는 이유: 타입에 따라 실행 컨텍스트를 생성하는 과정과 관리 내용이 다르기 때문

**전역 코드**

- 전역에 존재하는 코드 (함수, 클래스 내부 코드는 제외)
- 전역 스코프 생성, 전역 변수와 함수를 전역 객체의 프로퍼티/메서드로 바인딩하기 위해 전역 객체와 연결되어야 함
- 평가되면 **전역 실행 컨텍스트** 생성

**함수 코드**

- 함수 내부 코드 (중첩 함수 내부 코드는 제외)
- 지역 스코프 생성, 지역 변수 / 매개변수 / arguments 객체 관리
- 생성한 지역 스코프를 전역 스코프에서 시작하는 스코프 체인에 연결해야 함
- 평가되면 **함수 실행 컨텍스트** 생성

**eval 코드**

- strict mode에서 자신만의 독자적인 스코프 생성
- 평가되면 **eval 실행 컨텍스트** 생성

**모듈 코드**

- 모듈별로 독립적인 모듈 스코프 생성
- 평가되면 **모듈 실행 컨텍스트** 생성

### 소스코드의 평가와 실행

- 엔진은 소스코드를 **평가**와 **실행** 2단계로 처리
- 평가
    - 실행 컨텍스트 생성
    - 변수, 함수 등 **선언문만 먼저 실행**
    - 생성된 식별자를 키로 실행 컨텍스트가 관리하는 스코프에 등록
- 실행 (런타임 시작)
    - 선언문을 제외한 소스코드가 순차적으로 실행
    - 필요한 변수나 함수의 참조를 실행 컨텍스트가 관리하는 스코프에서 검색해서 취득
    - 변수 값 변경 등 실행 결과는 다시 스코프에 등록

```jsx
var x;  // 평가 단계에서 x 등록, undefined로 초기화
x = 1;  // 실행 단계에서 스코프에서 x 검색 후 값 할당
```

### 실행 컨텍스트의 역할

- 소스코드 실행에 필요한 환경을 제공하고 코드의 실행 결과를 실제로 관리하는 영역
- 흐름
    - 전역 코드 평가 → 전역 코드 실행 → 함수 호출 시 전역 코드 실행 일시 중단
    - 함수 코드 평가 → 함수 코드 실행 → 함수 종료 후 전역 코드로 복귀
- 코드 실행을 위해 필요한 것
    - 선언된 식별자를 스코프를 구분해서 등록하고 상태 변화를 관리
    - 스코프 체인을 통해 상위 스코프로 이동하며 식별자 검색
    - 현재 실행 중인 코드의 실행 순서 관리
- 식별자와 스코프는 **렉시컬 환경**으로, 코드 실행 순서는 **실행 컨텍스트 스택**으로 관리

### 실행 컨텍스트 스택

- 생성된 실행 컨텍스트는 스택 자료구조로 관리됨 → **실행 컨텍스트 스택 (콜 스택)**
- 전역 실행 컨텍스트 push → 함수 호출 시 함수 실행 컨텍스트 push → 종료 시 pop
- 스택 최상위에 있는 것이 **현재 실행 중인 실행 컨텍스트 (running execution context)**

### 렉시컬 환경

- 식별자와 식별자에 바인딩된 값, 그리고 상위 스코프에 대한 참조를 기록하는 자료구조
- 실행 컨텍스트를 구성하는 컴포넌트
- 키와 값을 갖는 객체 형태의 스코프를 생성해서 식별자를 키로 등록하고 바인딩된 값을 관리 → **스코프를 구분해서 식별자를 등록하고 관리하는 저장소**
- 실행 컨텍스트는 `LexicalEnvironment`와 `VariableEnvironment` 컴포넌트로 구성
    - 처음엔 둘 다 같은 렉시컬 환경을 참조하고, 특정 상황에서 분리됨 (책에서는 구분 없이 렉시컬 환경으로 통일)
- 렉시컬 환경의 구성
    - **환경 레코드 (Environment Record)**: 스코프에 포함된 식별자를 등록하고 바인딩된 값을 관리하는 저장소
    - **외부 렉시컬 환경에 대한 참조 (Outer Lexical Environment Reference)**: 상위 스코프를 가리킴 → 이걸로 **스코프 체인** 구현

### 실행 컨텍스트 생성과 식별자 검색 과정

#### 0. 전역 객체 생성

- 전역 코드 평가 전에 전역 객체가 먼저 생성됨 (빌트인 전역 프로퍼티/함수, 표준 빌트인 객체, 호스트 객체 포함)

#### 1. 전역 코드 평가

1. **전역 실행 컨텍스트 생성** → 실행 컨텍스트 스택에 push
2. **전역 렉시컬 환경 생성** → 전역 실행 컨텍스트에 바인딩
    - **전역 환경 레코드 생성**, 두 가지로 구성
        - **객체 환경 레코드**: `var` 전역 변수, 함수 선언문 전역 함수, 빌트인 전역 프로퍼티/함수, 표준 빌트인 객체 관리 → 전역 객체(BindingObject)와 연결되어서 전역 객체의 프로퍼티가 됨
        - **선언적 환경 레코드**: `let`, `const` 전역 변수 관리 → 그래서 전역 객체의 프로퍼티가 아님
    - `var`는 선언과 `undefined` 초기화가 동시에, 함수 선언문은 함수 객체가 바로 할당됨 → 호이스팅 동작 차이
    - `let`, `const`는 선언만 되고 초기화는 런타임에 → **TDZ**
    - **this 바인딩**: 전역 환경 레코드의 `[[GlobalThisValue]]`에 전역 객체 바인딩 (this 바인딩은 전역 환경 레코드와 함수 환경 레코드에만 존재)
    - **외부 렉시컬 환경 참조 결정**: 전역은 최상위라 `null` → 스코프 체인의 종점

#### 2. 전역 코드 실행

- 변수 할당문, 함수 호출문 실행
- **식별자 결정**: 현재 실행 중인 실행 컨텍스트의 렉시컬 환경에서 검색 시작 → 없으면 외부 렉시컬 환경 참조를 따라 상위로 → 전역에도 없으면 ReferenceError

#### 3. 함수 코드 평가

1. **함수 실행 컨텍스트 생성** (렉시컬 환경이 완성된 다음 스택에 push)
2. **함수 렉시컬 환경 생성**
    - **함수 환경 레코드 생성**: 매개변수, arguments 객체, 지역 변수, 중첩 함수 등록
    - **this 바인딩**: 함수 환경 레코드의 `[[ThisValue]]`에 바인딩, 함수 호출 방식에 따라 결정
    - **외부 렉시컬 환경 참조 결정**: **함수 정의가 평가된 시점**에 실행 중인 실행 컨텍스트의 렉시컬 환경
        - 함수는 정의될 때 상위 스코프를 자신의 내부 슬롯 `[[Environment]]`에 저장해 둠
        - 이게 **렉시컬 스코프**의 실체

#### 4. 함수 코드 실행

- 매개변수에 인수 할당, 변수 할당 등 순차 실행
- 식별자 검색은 똑같이 현재 렉시컬 환경 → 상위 렉시컬 환경 순
- `console.log` 같은 경우 `console`은 스코프 체인으로 전역까지 가서 찾고, `log`는 프로토타입 체인으로 검색

#### 5. 함수 코드 실행 종료

- 함수 실행 컨텍스트가 스택에서 pop
- 하지만 **렉시컬 환경은 누군가 참조하고 있으면 소멸하지 않음** → 클로저로 연결

### 실행 컨텍스트와 블록 레벨 스코프

- `let`, `const`는 블록 레벨 스코프를 따름
- 블록 코드 실행 시 **선언적 환경 레코드를 가진 새 렉시컬 환경**을 생성해서 기존 렉시컬 환경과 교체
    - 새 렉시컬 환경의 외부 참조는 블록 실행 전의 렉시컬 환경
- 블록 종료 시 원래 렉시컬 환경으로 복귀
- `for` 문에서 `let`을 쓰면 **반복할 때마다 새 렉시컬 환경** 생성 → 24장 클로저 실수 해결과 연결됨

## 24장 클로저

- 함수형 프로그래밍 언어에서 쓰이던 개념, 자바스크립트 고유 개념 아님
- MDN 정의: **"클로저는 함수와 그 함수가 선언된 렉시컬 환경과의 조합이다"**

### 렉시컬 스코프

- 함수를 **어디서 호출했는지가 아니라 어디서 정의했는지**에 따라 상위 스코프가 결정됨
- 렉시컬 환경의 "외부 렉시컬 환경 참조"에 저장될 값(상위 스코프)은 함수 정의가 평가되는 시점에 결정

### 함수 객체의 내부 슬롯 [[Environment]]

- 함수는 자신이 정의된 환경(상위 스코프)을 기억해야 함
- 함수 정의가 평가될 때, 현재 실행 중인 실행 컨텍스트의 렉시컬 환경을 **`[[Environment]]`에 저장**
- 함수가 호출되면 함수 렉시컬 환경의 외부 참조에 `[[Environment]]` 값이 할당됨

### 클로저와 렉시컬 환경

```jsx
const x = 1;

function outer() {
  const x = 10;
  const inner = function () { console.log(x); };
  return inner;
}

const innerFunc = outer();
innerFunc(); // 10
```

- `outer`는 이미 종료돼서 실행 컨텍스트 스택에서 제거됐는데 `inner`가 여전히 `x`를 참조함
- **외부 함수보다 중첩 함수가 더 오래 유지되는 경우, 중첩 함수는 생명 주기가 끝난 외부 함수의 변수를 참조할 수 있음** → 이 중첩 함수가 **클로저**
- 이유
    - outer의 실행 컨텍스트는 제거되지만 outer의 **렉시컬 환경은 inner의 `[[Environment]]`가 참조**하고 있음
    - 누군가 참조하고 있으니 GC 대상이 되지 않음
- 이론적으로는 모든 함수가 상위 스코프를 기억하니 클로저지만, 일반적으로는 다음 조건을 만족할 때만 클로저라고 부름
    - 중첩 함수가 **상위 스코프의 식별자를 참조**하고
    - 중첩 함수가 **외부 함수보다 더 오래 유지**됨
- 상위 스코프 식별자를 참조하지 않으면 클로저 아님 (브라우저는 최적화로 참조하지 않는 식별자는 기억하지 않음)
- 중첩 함수를 반환하지 않고 외부 함수 안에서만 쓰면 외부 함수보다 먼저 소멸 → 클로저의 본질에 맞지 않음
- 클로저가 참조하는 상위 스코프의 변수 = **자유 변수 (free variable)**
    - 클로저는 "자유 변수에 묶여 있는 함수"
    - 브라우저는 상위 스코프에서 자유 변수만 기억하므로 메모리 걱정은 크게 안 해도 됨

### 클로저의 활용

- **상태를 안전하게 변경하고 유지**하기 위해 사용
- 상태를 은닉하고, **특정 함수에게만 상태 변경을 허용**

```jsx
const increase = (function () {
  let num = 0; // 카운트 상태 (은닉)

  return function () {
    return ++num;
  };
}());

increase(); // 1
increase(); // 2
```

- 단계별로 보면
    - `num`을 전역 변수로 두면 누구나 변경 가능 → 위험
    - 함수 안의 지역 변수로 옮기면 호출할 때마다 0으로 초기화됨
    - **즉시 실행 함수 + 클로저**로 한 번만 초기화되고 외부에서 접근 불가한 상태 완성
- 여러 메서드가 필요하면 `{ increase, decrease }` 같은 객체를 반환 → 두 메서드가 같은 렉시컬 환경을 공유
- 생성자 함수로도 구현 가능 (prototype 메서드도 즉시 실행 함수의 렉시컬 환경을 참조하도록)
- 함수형 프로그래밍에서 고차 함수로 활용할 때 주의점
    - `makeCounter(aux)`처럼 호출할 때마다 클로저를 반환하는 함수는 **호출마다 새로운 렉시컬 환경** 생성
    - 그래서 `makeCounter(increase)`와 `makeCounter(decrease)`로 만든 카운터는 상태를 공유하지 않음
    - 공유하려면 즉시 실행 함수로 렉시컬 환경을 하나만 만들어 두고 그 안에서 클로저를 반환

### 캡슐화와 정보 은닉

- **캡슐화**: 프로퍼티(상태)와 메서드(동작)를 하나로 묶는 것
- **정보 은닉**: 캡슐화로 객체의 특정 프로퍼티나 메서드를 감추는 것 → 결합도를 낮춤
- 자바스크립트는 `public`, `private`, `protected` 같은 접근 제한자가 없음 → 기본적으로 모두 public
- 생성자 함수 안에서 `let _age`로 흉내 낼 수는 있음
    - 근데 prototype 메서드에서는 `_age`에 접근 불가
    - 즉시 실행 함수로 감싸서 해결하려 하면 **여러 인스턴스가 `_age`를 공유**해 버리는 문제
- 결국 클로저로는 완벽한 private 구현이 어려움 → 클래스의 **private 필드(`#`)** 로 해결 (25장)

### 자주 발생하는 실수

```jsx
var funcs = [];

for (var i = 0; i < 3; i++) {
  funcs[i] = function () { return i; };
}

for (var j = 0; j < funcs.length; j++) {
  console.log(funcsj); // 3 3 3
}
```

- `var`는 함수 레벨 스코프라 `i`가 전역 변수 하나 → 모든 함수가 같은 `i`(최종값 3)를 참조
- 해결
    - **즉시 실행 함수**로 `i`를 매개변수로 넘겨서 각각 캡처
    - **`let` 사용**: for 문이 반복마다 새 렉시컬 환경을 만들어서 각 함수가 그 시점의 `i`를 기억 → 가장 간단
    - 고차 함수 사용 (`Array.from({ length: 3 }, (_, i) => () => i)`)

## 25장 클래스

### 클래스는 프로토타입의 문법적 설탕인가?

- 자바스크립트는 **프로토타입 기반** 객체지향 언어, 클래스 없이도 생성자 함수 + 프로토타입으로 상속 구현 가능
- ES6 클래스도 결국 함수이고 프로토타입 기반으로 동작하지만, 생성자 함수와 똑같이 동작하진 않음
- 생성자 함수와의 차이
    - `new` 없이 호출하면 **에러**
    - `extends`, `super` 키워드로 상속 지원
    - 호이스팅이 **발생하지 않는 것처럼** 동작
    - 클래스 내 모든 코드는 **암묵적으로 strict mode**
    - constructor, 프로토타입 메서드, 정적 메서드 모두 **열거 불가** (`[[Enumerable]]: false`)
- 그래서 단순한 문법적 설탕이라기보다 **새로운 객체 생성 메커니즘**으로 보는 게 합당

### 클래스 정의

- `class` 키워드, 이름은 파스칼 케이스가 일반적
- 표현식으로도 정의 가능 → 클래스는 **일급 객체** (값처럼 쓸 수 있음)
- 몸체에 정의할 수 있는 메서드: **constructor, 프로토타입 메서드, 정적 메서드**

```jsx
class Person {
  constructor(name) {
    this.name = name; // 인스턴스 프로퍼티
  }

  sayHi() {           // 프로토타입 메서드
    console.log(`Hi ${this.name}`);
  }

  static sayHello() { // 정적 메서드
    console.log('Hello');
  }
}
```

### 클래스 호이스팅

- 클래스는 함수로 평가됨 (`typeof Person === 'function'`)
- 클래스 선언문도 호이스팅되지만 `let`, `const`처럼 **TDZ**에 빠짐 → 선언 전 참조 시 ReferenceError

### 인스턴스 생성

- 반드시 `new`로 호출
- 클래스 표현식에 붙인 이름은 클래스 몸체 내부에서만 사용 가능, 외부에서 그 이름으로 인스턴스 생성 불가

### 메서드

#### constructor

- 인스턴스를 생성하고 초기화하는 특수한 메서드, 이름 변경 불가
- 클래스 정의가 평가되면 constructor에 기술된 동작을 하는 함수 객체가 생성됨 → **클래스 자체가 constructor**
- 클래스 내에 **최대 1개**만 가능
- 생략하면 빈 constructor가 암묵적으로 정의됨
- 명시적으로 `return` 하지 말 것
    - 객체를 반환하면 this 대신 그 객체가 반환됨
    - 원시값은 무시되고 this 반환

#### 프로토타입 메서드

- 생성자 함수처럼 `prototype`에 직접 추가하지 않아도 클래스 몸체에 정의하면 기본적으로 프로토타입 메서드가 됨
- 인스턴스는 프로토타입 체인을 통해 상속받아 사용

#### 정적 메서드

- `static` 키워드 사용
- 클래스에 바인딩된 메서드라 **클래스로 호출**, 인스턴스로는 호출 불가

#### 정적 메서드 vs 프로토타입 메서드

- 속해 있는 프로토타입 체인이 다름
- 정적 메서드는 클래스로, 프로토타입 메서드는 인스턴스로 호출
- 정적 메서드는 인스턴스 프로퍼티를 참조할 수 없음
- 결국 기준은 **this 사용 여부**
    - 인스턴스 프로퍼티를 참조해야 함 → 프로토타입 메서드
    - 아니면 → 정적 메서드
- 정적 메서드는 전역에서 쓸 유틸리티 함수를 모으는 **네임스페이스** 역할로도 유용 (`Math.max`, `Number.isNaN` 등)

#### 클래스 메서드의 특징

- `function` 키워드를 생략한 메서드 축약 표현 사용
- 메서드 사이에 콤마 불필요
- 암묵적으로 strict mode
- 열거 불가
- **non-constructor** → `new`로 호출 불가

### 클래스의 인스턴스 생성 과정

1. **인스턴스 생성과 this 바인딩**: 빈 객체 생성, 그 프로토타입으로 클래스의 `prototype` 객체 설정, this에 바인딩
2. **인스턴스 초기화**: constructor 코드 실행, this에 프로퍼티 추가
3. **인스턴스 반환**: 완성된 인스턴스가 바인딩된 this를 암묵적으로 반환

### 프로퍼티

#### 인스턴스 프로퍼티

- constructor 내부에서 `this`에 추가
- 언제나 public

#### 접근자 프로퍼티

- `get`, `set` 키워드로 getter, setter 정의
- 호출하는 게 아니라 프로퍼티처럼 참조/할당하면 호출됨
- getter는 반드시 무언가를 반환, setter는 매개변수 1개
- 인스턴스가 아니라 **프로토타입의 프로퍼티**가 됨

#### 클래스 필드

```jsx
class Person {
  name = 'Lee'; // 클래스 필드
}
```

- 클래스 몸체에 인스턴스 프로퍼티를 직접 선언하는 문법 (책 집필 당시엔 제안 단계, ES2022에서 표준화)
- 클래스 몸체에서 `this` 사용 불가 (this는 constructor와 메서드 안에서만)
- 초기값을 할당하지 않으면 `undefined`
- 외부에서 받은 값으로 초기화해야 하면 결국 constructor에서 해야 함
- 함수를 할당할 수도 있지만 그러면 **프로토타입 메서드가 아니라 인스턴스 메서드**가 됨 → 권장 X

#### private 필드

```jsx
class Person {
  #name = '';

  constructor(name) {
    this.#name = name;
  }

  get name() {
    return this.#name;
  }
}
```

- 이름 앞에 `#`, 참조할 때도 `#` 붙임
- **클래스 내부에서만** 참조 가능 (인스턴스로 외부 접근, 자식 클래스 접근 불가)
- 외부에서는 접근자 프로퍼티로 간접 접근
- 반드시 **클래스 몸체에 정의**해야 함, constructor에서 바로 `this.#x = ...`로 정의하면 에러

#### static 필드

- `static` 필드, `static #private` 필드도 정의 가능

### 상속에 의한 클래스 확장

- 프로토타입 기반 상속은 프로토타입 체인으로 다른 객체의 자산을 상속받는 개념
- **상속에 의한 클래스 확장**은 기존 클래스를 상속받아 새로운 클래스를 확장해서 정의하는 것
- 생성자 함수는 상속 문법이 없음, 클래스는 `extends`로 기본 제공

#### extends 키워드

```jsx
class Animal { /* ... */ }
class Bird extends Animal { /* ... */ }
```

- 상속받는 클래스: **서브클래스** (파생 / 자식 클래스)
- 상속을 해주는 클래스: **수퍼클래스** (베이스 / 부모 클래스)
- 인스턴스의 프로토타입 체인뿐 아니라 **클래스 간의 프로토타입 체인**도 생성 → 정적 메서드도 상속됨

#### 동적 상속

- `extends` 뒤에는 클래스뿐 아니라 **`[[Construct]]`를 갖는 함수 객체로 평가되는 모든 표현식** 사용 가능
- 생성자 함수를 상속받을 수도 있고, 조건에 따라 상속 대상을 동적으로 결정할 수도 있음

#### 서브클래스의 constructor

- 생략하면 아래가 암묵적으로 정의됨

```jsx
constructor(...args) { super(...args); }
```

#### super 키워드

- **호출**하면 수퍼클래스의 constructor 호출
- **참조**하면 수퍼클래스의 메서드 호출 가능

**super 호출 주의사항**

- 서브클래스에서 constructor를 생략하지 않았다면 **반드시 `super()` 호출**
- **`super()` 호출 전에는 `this` 참조 불가**
- `super()`는 서브클래스의 constructor에서만 호출 가능

**super 참조**

- 메서드 안의 `super`는 수퍼클래스의 prototype을 가리킴 → `super.sayHi()`
- 메서드 축약 표현으로 정의된 메서드만 가능 (`[[HomeObject]]`를 가지기 때문)
- 정적 메서드 안의 `super`는 수퍼클래스의 정적 메서드를 가리킴

#### 상속 클래스의 인스턴스 생성 과정

- 클래스는 내부 슬롯 `[[ConstructorKind]]`로 수퍼클래스(`"base"`)와 서브클래스(`"derived"`)를 구분
- 서브클래스는 **직접 인스턴스를 만들지 않고 수퍼클래스에 위임** → 그래서 `super()` 호출이 필수
1. 서브클래스 constructor에서 `super()` 호출
2. **수퍼클래스가 인스턴스 생성, this 바인딩**
    - 이때 `new.target`은 서브클래스라서, 인스턴스의 프로토타입은 서브클래스의 `prototype`
3. 수퍼클래스 constructor로 인스턴스 초기화
4. **서브클래스 constructor로 복귀, super가 반환한 인스턴스를 this에 바인딩**
    - 서브클래스는 별도로 인스턴스를 만들지 않으니, 이게 `super()` 전에 this를 못 쓰는 이유
5. 서브클래스 constructor로 인스턴스 초기화
6. 완성된 인스턴스(this) 암묵적 반환

#### 표준 빌트인 생성자 함수 확장

```jsx
class MyArray extends Array {
  average() {
    return this.reduce((a, b) => a + b, 0) / this.length;
  }
}

const arr = new MyArray(1, 2, 3);
arr.filter(v => v > 1).average(); // 2.5
```

- `[[Construct]]`를 갖는 생성자 함수라면 `extends`로 확장 가능
- `filter`, `map` 같이 새 배열을 반환하는 메서드는 **MyArray 인스턴스를 반환** → 확장한 메서드로 체이닝 가능
- 이 동작을 바꾸고 싶으면 `static get Symbol.species`로 반환할 생성자 지정
