## 8장. 제어문

> 제어문은 **조건에 따라 코드 블록을 실행하거나 반복 실행할 때 사용**한다.

</br>

### 블록문

> 블록문은 0개 이상의 문을 중괄호로 묶은 것으로, 코드 블록 또는 블록이라고 부르기도 한다.

자바스크립트는 블록문을 하나의 실행 단위로 취급하고, 블록문은 단독으로 사용할 수도 있으나 일반적으로 제어문이나 함수를 정의할 때 사용된다.

블록문 자체로 종결성을 갖기 때문에 블록문 뒤에는 세미콜론을 붙이지 않는다.

</br>

### 조건문

> 조건문은 주어진 조건식의 평가 결과에 따라 코드 블록의 실행을 결정한다.

#### if-else문

- 조건식의 평가 결과에 따라 실행할 코드 블록을 결정한다.
- 조건식은 불리언 값이 아니어도 암묵적으로 타입 변환된다.
- 대부분의 if... else 문은 삼항 조건 연산자로 바꿔 쓸 수 있다. 단순히 값을 결정하는 경우에는 삼항 연산자, 실행할 코드 블록이 복잡한 경우에는 if... else문이 가독성이 좋다.

#### switch 문

- 주어진 표현식을 평가하여 그 값과 일치하는 case 문으로 실행 흐름을 옮긴다.
- if...else 문은 논리적 참/거짓으로 실행 흐름을 결정하지만, switch 문은 다양한 case에 따라 실행할 코드 블록을 결정할 때 유용하다.
- 폴스루(fall through): break 문을 생략하면 상관없이 다음 case 문으로 실행 흐름이 이어진다.
  의도적으로 폴스루를 이용하는 경우가 아니라면 반드시 break 문을 사용해야 한다.
- default 문은 마지막에 위치하므로= case 문과 달리 break 문이 필요 없다.

</br>

### 반복문

> 조건식의 평가 결과가 참인 경우 코드 블록을 실행하고, 조건식을 다시 평가하여 반복 여부를 결정한다.

#### for 문

- 반복 횟수가 명확할 때 가장 일반적으로 사용한다.
- `for (변수 선언문 또는 할당문; 조건식; 증감식) { ... }`
- 세 개의 표현식은 모두 옵션이며, 생략 시 무한루프가 된다(`for(;;) {}`).

#### while 문

- 조건식의 평가 결과가 참이면 계속 코드 블록을 실행한다.
- for 문은 반복 횟수가 명확할 때, while 문은 반복 횟수가 불명확할 때 주로 사용한다.
- 조건식 평가 결과가 항상 참이면 무한루프가 되며, 특정 조건이 되었을 때 `break` 문으로 탈출한다.

#### do...while 문

- 코드 블록을 먼저 실행하고 조건식을 평가한다. 따라서 코드 블록은 무조건 한 번 이상 실행된다.

</br>

### break 문

- 코드 블록을 탈출한다. label 문, 반복문(for, for...in, for...of, while, do...while), switch 문의 코드 블록에서만 사용 가능하다.
- 레이블 문(label statement)과 함께 사용하면 중첩된 for 문에서 외부 반복문까지 한 번에 탈출할 수 있다.

</br>

### continue 문

- 반복문의 코드 블록 실행을 현 지점에서 중단하고, 반복문의 증감식으로 실행 흐름을 이동시킨다. break 문처럼 반복문을 탈출하지는 않는다.
- if 문 내에서 실행해야 할 코드가 길다면, continue 문을 사용했을 때 else 문 없이도 else 문 사용 효과를 낼 수 있어 가독성이 좋아진다.

## 8장 딥다이브 Q&A

### for 문과 forEach 메서드는 어떤 차이가 있고, 언제 무엇을 선택해야 하나요?

<details>
<summary>답안</summary>
for 문은 언어 자체의 반복 제어 구문이라서 break, continue로 중간에 탈출하거나 다음 순회를 건너뛸 수 있고, 콜백 함수 호출 오버헤드가 없어 대용량 반복에서 성능상 유리합니다. 반면 forEach는 배열 메서드로 콜백 함수를 매 순회마다 호출하기 때문에 break가 불가능하고, return을 써도 콜백 함수만 종료될 뿐 반복 자체를 멈추지 못합니다. 또한 forEach 콜백 안에서 async/await를 사용해도 forEach 자체는 Promise를 기다려주지 않기 때문에 비동기 순회 순서를 보장하려면 for...of나 일반 for 문을 사용해야 합니다. 실무에서는 조기 종료가 필요 없고 가독성이 중요한 단순 순회에는 forEach나 map/filter 같은 고차 함수를, 성능이 중요하거나 중간 탈출이 필요한 경우에는 for 문을 선택하는 편입니다.
</details>

### for 문에서 var 대신 let을 사용해야 하는 이유를 설명해 주세요.

<details>
<summary>답안</summary>
var는 함수 레벨 스코프를 가지기 때문에 for 문의 변수 선언문에 var를 사용하면 반복마다 새로운 스코프가 생성되지 않고 전역(또는 함수) 스코프에 변수 하나만 존재하게 됩니다. 그래서 setTimeout이나 클로저 안에서 반복 변수를 참조하는 코드를 작성하면, 콜백이 실행되는 시점에는 이미 반복이 모두 끝난 뒤라 모든 콜백이 같은 최종값을 참조하는 문제가 발생합니다. 반면 let은 블록 레벨 스코프를 가지며, ES6 명세상 for 문의 각 반복마다 새로운 렉시컬 환경을 생성해 변수를 새로 바인딩하기 때문에 각 콜백이 자신의 순회 시점 값을 독립적으로 클로저로 캡처할 수 있습니다. 이는 클로저와 스코프 개념을 함께 이해하고 있는지 확인하는 대표적인 질문이라 원리까지 짚어서 답변하는 것이 좋습니다.
</details>

### switch 문에서 break를 생략하면 안 되는 이유(폴스루)와, 의도적으로 폴스루를 활용하는 사례가 있다면 무엇인가요?

<details>
<summary>답안</summary>
switch 문은 표현식의 평가 결과와 일치하는 case로 진입한 뒤, break 문을 만나지 않으면 이어지는 모든 case 블록을 순서대로 실행하는 폴스루 특성을 가지고 있습니다. 이를 의도치 않게 놓치면 여러 case가 동시에 실행되어 예상과 다른 부수효과가 발생하기 쉬우므로, 실무에서는 정적 분석 도구나 린트 규칙(예: ESLint no-fallthrough)으로 이를 강제하는 경우가 많습니다. 다만 여러 case 값에 대해 동일한 로직을 적용하고 싶을 때는 폴스루를 의도적으로 활용해 case를 연달아 나열하고 마지막에만 break를 두는 방식으로 코드 중복을 줄일 수 있습니다. 이 경우에는 주석으로 "폴스루 의도됨(falls through)"을 명시해 다른 개발자가 실수로 추가한 것이 아님을 알려주는 것이 좋은 컨벤션입니다.
</details>

### 중첩된 반복문에서 break나 continue로 바깥쪽 반복문까지 제어하려면 어떻게 하나요? 
<details>
<summary>답안</summary>
자바스크립트는 레이블 문(label statement)을 지원해서 반복문 앞에 식별자를 붙이고 `break 레이블` 또는 `continue 레이블` 형태로 중첩된 바깥쪽 반복문까지 한 번에 탈출하거나 건너뛸 수 있습니다. 하지만 실무에서는 레이블 문을 goto문과 유사하게 코드 흐름을 예측하기 어렵게 만든다는 이유로 잘 사용하지 않고, 대신 반복 로직을 함수로 분리해 return 문으로 탈출하거나, 플래그 변수와 조건을 조합해 가독성을 높이는 방식을 선호합니다. 예를 들어 이중 for 문에서 특정 조건을 만족하면 즉시 전체 탐색을 멈춰야 한다면, 그 로직 자체를 별도 함수로 추출하고 조건 만족 시 return하는 패턴이 더 명확합니다. 이런 답변은 단순히 문법을 아는 것을 넘어 코드 품질과 유지보수성까지 고려하는 시야를 보여줄 수 있는 포인트입니다.
</details>

### 삼항 조건 연산자(? :)를 중첩해서 사용하는 것이 안티패턴으로 여겨지는 이유는 무엇인가요?

<details>
<summary>답안</summary>
삼항 연산자는 표현식이기 때문에 값을 반환해야 하는 문맥(변수 할당, JSX 렌더링 등)에서 if...else보다 간결하게 쓸 수 있다는 장점이 있습니다. 하지만 삼항 연산자를 중첩해서 사용하면 조건과 결과가 한 줄에 겹겹이 쌓여 코드를 눈으로 따라가며 파싱하기 어려워지고, 어떤 조건이 어떤 결과에 대응하는지 실수로 잘못 읽을 위험이 커집니다. 그래서 팀 컨벤션이나 린트 규칙으로 삼항 연산자의 중첩을 금지하고, 값 하나를 단순 분기하는 경우에만 단일 삼항 연산자를 허용하며 조건이 복잡해지면 if...else 또는 함수로 분리하는 경우가 많습니다. 결국 삼항 연산자 사용 여부의 기준은 문법적으로 가능한지가 아니라, 코드를 읽는 사람이 즉시 이해할 수 있는지에 달려 있다고 답하는 것이 좋습니다.
</details>

## 9장. 타입 변환과 단축 평가

### 타입 변환이란?

기존 원시 값을 사용해 다른 타입의 새로운 원시 값을 생성하는 것을 타입 변환이라 한다. 개발자가 의도적으로 값의 타입을 변환하는 것을 **명시적 타입 변환**, 개발자의 의도와 상관없이 표현식을 평가하는 도중에 자바스크립트 엔진에 의해 암묵적으로 타입이 자동 변환되는 것을 **암묵적 타입 변환**이라 한다. 어느 쪽이든 기존 원시 값을 직접 변경하는 것이 아니라, 새로운 타입의 원시 값을 생성해 표현식을 평가하는 데 사용할 뿐이라는 점이 핵심이다.

</br>
 
### 암묵적 타입 변환
자바스크립트 엔진은 표현식을 평가할 때 개발자의 의도와 상관없이 코드의 문맥을 고려해 암묵적으로 데이터 타입을 강제 변환할 때가 있다.
 
### 2-1. 문자열 타입으로 변환
- `+` 연산자는 피연산자 중 하나 이상이 문자열이면 문자열 연결 연산자로 동작한다.
- 템플릿 리터럴의 표현식 삽입은 표현식의 평가 결과를 문자열 타입으로 암묵적 변환한다.
```js
1 + "2"; // "12"
`1 + 1 = ${1 + 1}`; // "1 + 1 = 2"
```
 
#### 숫자 타입으로 변환
- `+` 연산자를 제외한 산술 연산자는 피연산자를 숫자 타입으로 암묵적 변환한다. 숫자로 변환할 수 없는 경우 NaN이 된다.
- 비교 연산자도 피연산자를 숫자 타입으로 암묵적 변환한다.
- 단항 연산자 `+`를 값 앞에 붙이면 숫자 타입으로 변환된다(형변환 없이 표현식만 평가해도 발생).
```js
1 - "1"; // 0
1 * "10"; // 10
1 > "0"; // true
+"10"; // 10
+true; // 1
+null; // 0
+undefined; // NaN
+{}; // NaN
+[]; // 0
+[10, 20]; // NaN
```
 
#### 불리언 타입으로 변환
- 자바스크립트 엔진은 불리언 타입이 아닌 값을 Truthy 값(참으로 평가되는 값) 또는 Falsy 값(거짓으로 평가되는 값)으로 구분한다.
- Falsy 값: `false`, `undefined`, `null`, `0`, `-0`, `NaN`, `''`(빈 문자열). 이 외의 모든 값은 Truthy 값이다.
- 주의할 Truthy 값: `'0'`(문자열 '0'), `[]`(빈 배열), `{}`(빈 객체)는 모두 Truthy 값이다.

</br>

### 명시적 타입 변환

표준 빌트인 생성자 함수(String, Number, Boolean)를 new 연산자 없이 호출하거나, 빌트인 메서드, 암묵적 타입 변환을 이용하는 방법 등이 있다.

```js
// 문자열 타입으로 변환
String(1); // "1"
(1).toString(); // "1"
1 + ""; // "1"

// 숫자 타입으로 변환
Number("10"); // 10
parseInt("10"); // 10
+"10"; // 10
"10" * 1; // 10

// 불리언 타입으로 변환
Boolean("x"); // true
Boolean(""); // false
!!"x"; // true
```

</br>

### 단축 평가

논리곱(`&&`)과 논리합(`||`) 연산자 표현식의 평가 결과는 불리언 값이 아닐 수도 있다. 논리 연산의 결과를 결정하는 두 번째 피연산자, 즉 논리 연산의 결과를 결정하는 시점에 나머지 평가 과정을 생략하는 것을 단축 평가라 한다.

- `단축 평가` = 표현식을 평가하는 도중에 평가 결과가 확정된 경우 나머지 평가 과정을 생략하는 것.
- 논리곱(`&&`): 두 개의 피연산자가 모두 true일 때 true를 반환하므로, 좌항이 Falsy 값이면 좌항을 그대로 반환하고 나머지는 평가하지 않는다.
- 논리합(`||`): 두 개의 피연산자 중 하나만 true여도 true를 반환하므로, 좌항이 Truthy 값이면 좌항을 그대로 반환하고 나머지는 평가하지 않는다.

```js
"Cat" && "Dog"; // "Dog" (좌항이 Truthy이므로 우항까지 평가)
false && "Dog"; // false (좌항이 Falsy이므로 우항 평가 생략)

"Cat" || "Dog"; // "Cat" (좌항이 Truthy이므로 우항 평가 생략)
false || "Dog"; // "Dog" (좌항이 Falsy이므로 우항까지 평가)
```

#### 단축 평가의 활용

**객체를 가리키기를 기대하는 변수가 null/undefined가 아닌지 확인하고 프로퍼티를 참조할 때**

```js
var elem = null;
var value = elem && elem.value; // null
```

**함수 매개변수에 기본값을 설정할 때**

```js
function getStringLength(str) {
  str = str || "";
  return str.length;
}
```

#### 옵셔널 체이닝 연산자 (`?.`)

- 좌항의 피연산자가 null 또는 undefined인 경우 undefined를 반환하고, 그렇지 않으면 우항의 프로퍼티 참조를 이어간다.
- ES11(ECMAScript2020)에 도입되었다.
- `&&` 연산자는 좌항이 Falsy 값(0이나 ''도 포함)이면 좌항을 그대로 반환하지만, 옵셔널 체이닝은 좌항이 `null`/`undefined`일 때만 undefined를 반환한다는 차이가 있다.

```js
var elem = null;
var value = elem?.value; // undefined

var str = "";
var length = str && str.length; // "" (Falsy이므로 좌항 그대로 반환)
var length2 = str?.length; // 0 (str이 null/undefined가 아니므로 우항 평가)
```

</br>

#### 널 병합 연산자 (`??`)

- 좌항의 피연산자가 null 또는 undefined인 경우 우항의 피연산자를 반환하고, 그렇지 않으면 좌항의 피연산자를 반환한다.
- ES11에 도입되었으며, 변수에 기본값을 설정할 때 유용하다.
- `||` 연산자는 좌항이 Falsy 값이면 우항을 반환하지만, `??`는 좌항이 `null`/`undefined`일 때만 우항을 반환한다는 차이가 있다.

```js
var foo = "" || "default"; // "default" (Falsy이므로 우항 반환)
var bar = "" ?? "default"; // "" (null/undefined가 아니므로 좌항 반환)
```

</br>

## 9장 딥다이브 Q&A

### `||` 연산자와 `??`(널 병합 연산자)의 차이를 예시와 함께 설명해 주세요.

<details>
<summary>답안</summary>
`||` 연산자는 좌항 피연산자가 Falsy 값이기만 하면 무조건 우항 피연산자를 평가해서 반환하기 때문에, 좌항이 `0`이나 `''`(빈 문자열)처럼 의도적으로 설정한 값이어도 Falsy로 취급되어 우항 값으로 덮어써지는 문제가 발생할 수 있습니다. 반면 `??` 연산자는 좌항이 오직 `null`이나 `undefined`일 때만 우항을 반환하기 때문에, 숫자 0이나 빈 문자열처럼 유효한 값을 기본값으로 대체하지 않고 그대로 보존할 수 있습니다. 예를 들어 사용자가 입력한 할인율이 0일 때 `discount || 10`은 의도치 않게 10을 반환하지만 `discount ?? 10`은 0을 그대로 반환해 실제 값을 보존합니다. 그래서 실무에서는 숫자나 불리언처럼 falsy이지만 유효한 값을 다룰 때는 `??`를, 문자열이 비어있거나 값이 아예 없을 때를 함께 처리하고 싶을 때는 `||`를 의도적으로 선택하는 것이 중요합니다.
</details>

### 옵셔널 체이닝(`?.`)이 나오기 전에는 어떻게 안전하게 중첩 프로퍼티에 접근했고, 옵셔널 체이닝은 이를 어떻게 개선했나요?

<details>
<summary>답안</summary>
옵셔널 체이닝 이전에는 `user && user.address && user.address.city`처럼 `&&` 연산자를 체이닝하거나, 중첩된 if 문으로 각 단계마다 null/undefined 여부를 일일이 검사해야 했기 때문에 프로퍼티 깊이가 깊어질수록 코드가 장황해지고 가독성이 떨어졌습니다. 옵셔널 체이닝은 `user?.address?.city`처럼 체이닝 도중 어느 한 단계라도 null 또는 undefined를 만나면 즉시 평가를 멈추고 undefined를 반환하기 때문에, 짧고 읽기 쉬운 코드로 동일한 안전성을 확보할 수 있습니다. 또한 `&&` 체이닝은 falsy 값(0이나 빈 문자열)을 만나도 그 값을 그대로 반환해버리는 부작용이 있었는데, 옵셔널 체이닝은 오직 null/undefined 여부만 검사하므로 이런 falsy 값 문제에서 자유롭습니다. 함수 호출에도 `user.getName?.()`처럼 사용할 수 있어 메서드 존재 여부 확인에도 활용도가 높습니다.
</details>

### `+` 연산자가 문맥에 따라 산술 연산자로도, 문자열 연결 연산자로도 동작하는 원리는 무엇이며, 이로 인해 발생할 수 있는 버그를 어떻게 방지하나요?

<details>
<summary>답안</summary>
`+` 연산자는 자바스크립트 엔진이 두 피연산자를 평가할 때 피연산자 중 하나라도 문자열이면 문자열 연결 연산으로, 둘 다 숫자면 산술 덧셈으로 동작하도록 암묵적 타입 변환을 수행하기 때문에 이중적인 동작을 보입니다. 이 때문에 API 응답이나 폼 입력값처럼 실제로는 숫자를 담고 있지만 타입이 문자열인 값을 무심코 더하면 `"1" + 1`이 `11`이 아니라 `"11"`이 되는 식으로 의도치 않은 문자열 연결이 발생하는 대표적인 버그 원인이 됩니다. 이를 방지하려면 연산 전에 `Number()`나 단항 `+` 연산자로 명시적으로 타입을 변환해 의도를 코드에 드러내거나, TypeScript처럼 정적 타입 검사를 도입해 컴파일 시점에 타입 불일치를 잡아내는 방법을 사용합니다. 실무에서는 서버에서 내려오는 숫자 데이터가 문자열로 직렬화되어 오는 경우가 흔하기 때문에, API 응답을 다룰 때 타입 변환을 습관화하는 것이 중요합니다.
</details>

### 배열이나 객체가 Truthy 값으로 취급된다는 점 때문에 발생할 수 있는 실수는 무엇이고, 빈 배열/빈 객체를 검사하려면 어떻게 해야 하나요?

<details>
<summary>답안</summary>
자바스크립트에서 Falsy 값은 `false`, `undefined`, `null`, `0`, `-0`, `NaN`, `''` 일곱 가지뿐이며, 빈 배열 `[]`과 빈 객체 `{}`는 내용이 비어 있어도 모두 Truthy 값으로 평가됩니다. 그래서 `if (arr)`처럼 배열이 존재하는지만 확인하려는 의도로 조건문을 작성하면, 배열이 비어 있는 경우에도 조건이 참으로 평가되어 원하는 분기 로직이 실행되지 않는 실수가 흔히 발생합니다. 배열이 비어 있는지 확인하려면 `arr.length === 0`처럼 length 프로퍼티를 직접 검사해야 하고, 객체가 비어 있는지 확인하려면 `Object.keys(obj).length === 0`처럼 열거 가능한 프로퍼티 개수를 확인해야 합니다. 이런 문제는 단순히 문법을 아는지보다 자바스크립트의 타입 변환 규칙을 정확히 이해하고 있는지를 보여주는 질문이라, Truthy/Falsy의 정확한 목록을 암기해두는 것이 좋습니다.
</details>

### 단축 평가를 활용해 함수 매개변수의 기본값을 설정하는 기존 패턴(`str = str || ''`)이, ES6의 매개변수 기본값 문법과 어떤 차이가 있나요?

<details>
<summary>답안</summary>
단축 평가를 이용한 `str = str || ''` 패턴은 인자로 전달된 값이 Falsy이기만 하면 무조건 기본값으로 대체하기 때문에, 호출자가 의도적으로 `0`이나 `''`, `false`를 전달했더라도 이를 무시하고 기본값으로 덮어써버리는 문제가 있습니다. 반면 ES6의 매개변수 기본값 문법(`function f(str = '') {}`)은 인자가 아예 전달되지 않았거나 명시적으로 `undefined`를 전달한 경우에만 기본값을 적용하고, `0`이나 `false`처럼 falsy이지만 유효한 인자는 그대로 사용한다는 점에서 더 정확한 의도를 표현할 수 있습니다. 그래서 최신 코드에서는 단순 기본값 설정에는 매개변수 기본값 문법을, null/undefined 여부와 무관하게 falsy 값 자체를 걸러내고 싶은 경우에만 단축 평가나 `??`를 상황에 맞게 선택해서 사용하는 것이 좋습니다. 이 둘의 차이를 정확히 아는 것은 함수 설계 시 예상치 못한 인자 값을 얼마나 안전하게 다루는지와 직결되는 중요한 포인트입니다.
</details>

</br>

## 10장. 객체 리터럴

### 객체란?

자바스크립트는 객체 기반의 언어이며, 원시 값을 제외한 나머지 값(함수, 배열, 정규 표현식 등)은 모두 객체다. 원시 타입은 단 하나의 값만 나타내지만, 객체 타입은 다양한 타입의 값(원시 값 또는 다른 객체)을 하나의 단위로 구성한 자료구조다. 객체는 0개 이상의 프로퍼티(property)로 구성된 집합이며, 프로퍼티는 키와 값으로 구성된다. 프로퍼티 값이 함수인 경우 일반 함수와 구분하기 위해 메서드(method)라고 부른다.

</br>
 
### 객체 리터럴에 의한 객체 생성
 
- C++, 자바 같은 클래스 기반 객체지향 언어는 클래스를 사전에 정의하고 필요할 때 new 연산자로 인스턴스를 생성하지만, 자바스크립트는 객체 리터럴, Object 생성자 함수, 생성자 함수, Object.create 메서드, 클래스(ES6) 등 다양한 방법으로 객체를 생성할 수 있다.
- 그중 가장 일반적이고 간편한 방법이 객체 리터럴이다. 중괄호(`{}`) 내에 0개 이상의 프로퍼티를 정의하며, 객체 리터럴은 값으로 평가되는 표현식이므로 세미콜론을 붙인다.
```js
var person = {
  name: "Lee",
  sayHello: function () {
    console.log(`Hello! My name is ${this.name}.`);
  },
};
```

</br>

### 프로퍼티

- 프로퍼티 키: 빈 문자열을 포함하는 모든 문자열 또는 심벌 값. 식별자 네이밍 규칙을 따르지 않는 이름은 반드시 따옴표로 감싸야 한다.
- 프로퍼티 키에 문자열이나 심벌 값 외의 값을 사용하면 암묵적 타입 변환을 통해 문자열이 된다.
- 이미 존재하는 프로퍼티 키를 중복 선언하면 나중에 선언한 프로퍼티가 먼저 선언한 프로퍼티를 덮어쓴다(에러 발생 없음).

</br>

### 프로퍼티 접근

- **마침표 표기법(dot notation)**: `person.name`
- **대괄호 표기법(bracket notation)**: `person["name"]`. 대괄호 안에는 반드시 따옴표로 감싼 문자열이어야 하며, 그렇지 않으면 식별자로 해석되어 에러가 발생하거나 의도치 않게 동작한다.
- 객체에 존재하지 않는 프로퍼티에 접근하면 undefined를 반환한다(에러가 아님).

```js
var person = { name: "Lee" };
person.name; // "Lee"
person["name"]; // "Lee"
person[name]; // ReferenceError (따옴표 없이 식별자로 해석)
person.age; // undefined
```

</br>

### 프로퍼티 값 갱신, 동적 생성, 삭제

- 이미 존재하는 프로퍼티에 값을 할당하면 프로퍼티 값이 갱신된다.
- 존재하지 않는 프로퍼티에 값을 할당하면 프로퍼티가 동적으로 생성되어 추가된다.
- `delete` 연산자로 프로퍼티를 삭제할 수 있다. 존재하지 않는 프로퍼티를 삭제해도 에러 없이 무시된다.

</br>

### ES6에서 추가된 객체 리터럴 확장 기능

#### 프로퍼티 축약 표현

변수 이름과 프로퍼티 키 이름이 동일한 경우 프로퍼티 키를 생략(축약)할 수 있다. 이때 프로퍼티 키는 변수 이름으로 자동 생성된다.

```js
let x = 1,
  y = 2;
const obj = { x, y }; // { x: 1, y: 2 }
```

#### 계산된 프로퍼티 이름

문자열 또는 문자열로 타입 변환할 수 있는 값으로 평가되는 표현식을 사용해 대괄호(`[]`)로 프로퍼티 키를 동적으로 생성할 수 있다.

```js
const prefix = "prop";
let i = 0;
const obj = {
  [`${prefix}-${++i}`]: i,
  [`${prefix}-${++i}`]: i,
}; // { "prop-1": 1, "prop-2": 2 }
```

#### 메서드 축약 표현

ES6에서는 메서드를 정의할 때 function 키워드를 생략한 축약 표현을 사용할 수 있다. 이 축약 표현으로 정의한 메서드는 프로퍼티에 할당한 일반 함수와 달리 내부적으로 [[HomeObject]]를 갖기 때문에 `super` 키워드를 사용할 수 있다는 차이가 있다.

```js
const obj = {
  name: "Lee",
  sayHi() {
    console.log(`Hi! ${this.name}`);
  },
};
```

</br>
 
## 10장 딥다이브 Q&A
 
### 프로퍼티 접근 시 마침표 표기법(dot notation)과 대괄호 표기법(bracket notation)은 각각 언제 사용해야 하나요?
<details>
<summary>답안</summary>
마침표 표기법은 프로퍼티 키가 자바스크립트 식별자 네이밍 규칙을 따르는, 즉 코드 작성 시점에 키 이름을 정확히 알고 있는 경우에 간결하게 사용할 수 있습니다. 반면 대괄호 표기법은 프로퍼티 키가 하이픈이 포함되거나 숫자로 시작하는 등 식별자 규칙을 따르지 않는 경우, 또는 변수나 표현식의 평가 결과로 프로퍼티 키가 동적으로 결정되는 경우에 필수적으로 사용해야 합니다. 예를 들어 API 응답 객체를 순회하면서 `for...in`이나 `Object.keys()`로 얻은 키 변수로 값을 조회할 때는 `obj[key]`처럼 대괄호 표기법을 쓸 수밖에 없습니다. 실무에서는 정적인 키에는 가독성이 좋은 마침표 표기법을, 동적인 키 접근이 필요한 상황에서만 대괄호 표기법을 선택적으로 사용하는 것이 일반적인 컨벤션입니다.
</details>

### ES6 메서드 축약 표현으로 정의한 메서드와, 프로퍼티에 익명 함수 표현식을 할당해 정의한 메서드는 동작에 어떤 차이가 있나요?

<details>
<summary>답안</summary>
겉보기에는 둘 다 객체의 메서드로 동작하지만, ES6 메서드 축약 표현으로 정의한 함수는 내부적으로 `[[HomeObject]]`라는 내부 슬롯을 가지고 있어서 `super` 키워드를 사용해 프로토타입 체인 상의 상위 객체 메서드를 참조할 수 있다는 차이가 있습니다. 반면 `sayHi: function() {}`처럼 일반 함수 표현식을 프로퍼티에 할당한 경우에는 `[[HomeObject]]`가 없기 때문에 그 함수 내부에서 `super`를 사용하면 문법 에러가 발생합니다. 이 차이는 클래스 문법이나 프로토타입 기반 상속 구조에서 상위 객체의 동일한 이름의 메서드를 오버라이딩하면서도 원래 구현을 재사용하고 싶을 때 실질적으로 영향을 미칩니다. 실무에서는 객체 리터럴이나 클래스 내부에서 메서드를 정의할 때 습관적으로 축약 표현을 사용하는 것이 일반적이며, 이 내부 동작 차이는 상속 관련 심화 질문에서 함께 다뤄지는 경우가 많습니다.
</details>

### 객체 리터럴 방식과 생성자 함수(또는 클래스) 방식으로 객체를 생성하는 것은 각각 언제 선택해야 하나요?

<details>
<summary>답안</summary>
객체 리터럴은 단 하나의 객체만 생성하면 되는 경우, 즉 동일한 구조를 가진 여러 인스턴스를 만들 필요가 없는 설정 객체나 일회성 데이터 구조를 정의할 때 가장 간결하고 직관적인 방법입니다. 반면 생성자 함수나 클래스는 동일한 프로퍼티와 메서드 구조를 가진 객체를 여러 개 생성해야 할 때, 프로토타입을 통해 메서드를 공유함으로써 메모리를 절약하고 객체마다 필요한 초기화 로직(생성자)을 캡슐화할 수 있다는 장점이 있습니다. 예를 들어 여러 사용자 데이터를 다루는 User라는 개념이 있고 각 인스턴스가 동일한 메서드(예: getFullName)를 공유해야 한다면 클래스로 설계하는 것이 프로토타입 메서드 공유 측면에서 훨씬 효율적입니다. 반대로 API 응답을 그대로 받아 사용하거나 컴포넌트에 전달할 단순 설정값을 담는 경우라면 객체 리터럴로 충분하고 오히려 클래스를 쓰는 것이 과도한 설계가 될 수 있습니다.
</details>

## 11장. 원시 값과 객체의 배교

### 원시 값

#### 변경 불가능한 값

원시 타입의 값, 즉 원시 값은 변경 불가능한 값(immutable value)이다. 한번 생성된 원시 값은 읽기 전용(read only) 값으로서 변경할 수 없다. 변경 불가능하다는 것은 변수가 아니라 값에 대한 진술이다. 원시 값을 변수에 재할당하면 변경 불가능한 기존 값을 변경하는 것이 아니라, 새로운 메모리 공간을 확보하고 재할당한 값을 저장한 후 변수가 참조하던 메모리 공간의 주소를 변경하는 것이다.

```js
var str = "Hello";
str = "world"; // 새로운 문자열 "world"가 생성되고 변수는 이를 재할당받음(기존 "Hello"는 불변)
```

#### 문자열과 불변성

문자열은 유사 배열 객체이면서 이터러블이기 때문에 배열처럼 인덱스를 통해 각 문자에 접근할 수 있다. 하지만 문자열은 원시 값이므로 변경이 불가능하다. 인덱스를 사용해 특정 문자를 변경하려고 하면 에러가 발생하지 않지만 아무런 효과도 없다.

```js
var str = "string";
str[0] = "S"; // 에러는 없지만 반영되지 않음
console.log(str); // "string"
```

#### 값에 의한 전달

변수에 원시 값을 갖는 변수를 할당하면 원본의 값이 복사되어 전달된다. 이를 값에 의한 전달이라 한다. 이때 두 변수의 값은 다른 메모리 공간에 저장된 별개의 값이므로 한 변수의 값을 변경해도 다른 변수에는 어떠한 영향도 주지 않는다.

```js
var score = 80;
var copy = score;
score = 100;
console.log(copy); // 80 (영향 없음)
```

</br>

### 객체

#### 변경 가능한 값 (Mutable value)

객체(참조) 타입의 값, 즉 객체는 변경 가능한 값이다. 객체를 할당한 변수가 기억하는 메모리 공간에는 실제 객체가 아니라 생성된 객체가 저장된 메모리 공간의 주소, 즉 참조 값이 저장된다. 객체를 생성하고 프로퍼티 값을 갱신, 추가, 삭제해도 참조 값은 변경되지 않는다.

#### 참조에 의한 전달 (Pass by reference)

객체를 가리키는 변수를 다른 변수에 할당하면 원본의 참조 값이 복사되어 전달되는데, 이를 참조에 의한 전달이라 한다. 이 경우 두 개의 변수(원본과 복사본)가 모두 동일한 객체를 참조하기 때문에 어느 한쪽에서 객체를 변경하면 다른 한쪽에도 그 변경이 반영된다. 원본과 사본 모두 동일한 참조 값을 가지므로 사실상 두 개의 식별자가 하나의 객체를 공유하는 것이다.

```js
var person = { name: "Lee" };
var copy = person;

copy.name = "Kim";
console.log(person.name); // "Kim" (원본도 변경됨, 참조를 공유하기 때문)

console.log(person === copy); // true (참조 값 비교)
```

> **참고**: 엄밀히 말하면 자바스크립트에는 "참조에 의한 전달"이 별도로 존재하는 것이 아니라, 객체의 경우에도 참조 값(메모리 주소) 자체가 복사되어 전달된다는 점에서 사실상 값에 의한 전달과 동일한 매커니즘으로 볼 수 있다는 관점도 있다. 다만 이 책에서는 편의상 원시 값 전달과 구분하기 위해 참조에 의한 전달이라는 용어를 사용한다.

## 11장 딥다이브 Q&A

### "자바스크립트는 값에 의한 전달만 존재한다"는 주장과 "원시 값은 값에 의한 전달, 객체는 참조에 의한 전달"이라는 주장이 둘 다 있는데, 이 둘을 어떻게 이해하고 설명하면 좋을까요?

<details>
<summary>답안</summary>
두 주장은 사실 같은 현상을 다른 층위에서 설명하는 것으로, 변수에 값을 재할당하거나 함수 인자로 전달할 때 자바스크립트 엔진은 항상 변수가 가진 값을 복사해서 전달한다는 점에서는 언제나 값에 의한 전달이라고 볼 수 있습니다. 다만 원시 값의 경우 변수가 가진 값 자체가 데이터 그 자체이지만, 객체의 경우 변수가 실제로 가진 값은 객체가 저장된 메모리 주소, 즉 참조 값이기 때문에 이 참조 값이 복사되어 전달되는 것이지 객체 자체가 복사되는 것이 아닙니다. 그래서 결과적으로 두 변수가 동일한 참조 값(같은 주소)을 공유하게 되어 한쪽에서 객체 내부를 변경하면 다른 쪽에서도 그 변경이 관찰되는데, 이 현상 때문에 관용적으로 "참조에 의한 전달"이라는 표현을 사용하는 것입니다. 면접에서는 이 두 관점이 모순되지 않으며, 참조 값도 결국 값이기 때문에 근본 메커니즘은 값에 의한 전달로 통일해서 설명할 수 있다는 점까지 짚어주면 이해도를 잘 보여줄 수 있습니다.
</details>

### 객체를 다른 변수에 할당하거나 함수 인자로 넘겼을 때 원본이 의도치 않게 변경되는 문제를 방지하려면 어떻게 해야 하나요? 얕은 복사와 깊은 복사의 차이도 설명해 주세요.

<details>
<summary>답안</summary>
객체는 참조 값이 공유되기 때문에 원본을 보호하려면 새로운 객체를 만들어 복사해야 하는데, 스프레드 문법(`{ ...obj }`)이나 `Object.assign({}, obj)`으로 만드는 복사는 얕은 복사(shallow copy)로, 최상위 프로퍼티만 새로운 참조로 복사될 뿐 프로퍼티 값이 중첩된 객체나 배열이면 그 내부는 여전히 원본과 참조를 공유합니다. 그래서 중첩된 객체까지 완전히 독립적으로 분리하려면 `structuredClone()` 같은 내장 API나 `JSON.parse(JSON.stringify(obj))`, 혹은 lodash의 `cloneDeep` 같은 라이브러리를 사용해 깊은 복사(deep copy)를 수행해야 합니다. 다만 `JSON.parse(JSON.stringify())` 방식은 함수, undefined, Symbol, Date 객체 등을 제대로 직렬화하지 못하는 한계가 있어 실무에서는 `structuredClone`이나 검증된 라이브러리를 선호하는 편입니다. 이 질문은 단순히 API를 나열하는 것보다, 왜 얕은 복사만으로는 부족한지 참조 공유 원리와 연결해서 설명하는 것이 중요합니다.
</details>

### `const`로 선언한 객체 변수의 프로퍼티는 왜 변경이 가능한가요? const의 불변성은 정확히 무엇을 보장하는 건가요?

<details>
<summary>답안</summary>
`const`가 보장하는 것은 변수에 저장된 값(바인딩) 자체를 재할당할 수 없다는 것이지, 그 값이 가리키는 데이터의 내용까지 변경할 수 없다는 뜻은 아닙니다. 객체를 `const`로 선언한 경우 변수에는 객체의 참조 값(메모리 주소)이 저장되는데, 프로퍼티를 추가하거나 값을 변경하는 작업은 참조 값 자체를 바꾸는 것이 아니라 그 참조가 가리키는 객체의 내부 상태를 바꾸는 것이므로 const의 제약과 충돌하지 않습니다. 반면 `person = {}`처럼 변수 자체에 새로운 객체를 재할당하려는 시도는 참조 값을 바꾸는 행위이므로 const 제약을 위반해 에러가 발생합니다. 만약 객체 내부 프로퍼티까지 변경되지 않도록 강제하고 싶다면 `Object.freeze()`를 사용해 객체를 동결해야 하며, 이때도 중첩 객체까지는 얼려지지 않는다는 점(얕은 동결)을 함께 알아두는 것이 좋습니다.
</details>

### 함수에 객체를 인자로 전달했을 때, 함수 내부에서 그 객체의 프로퍼티를 변경하면 함수 바깥의 원본 객체에도 영향을 미치나요? 이를 활용하거나 방지하는 실무 패턴을 설명해 주세요.

<details>
<summary>답안</summary>
함수 인자로 객체를 전달하면 매개변수는 원본과 동일한 참조 값을 복사해서 갖게 되므로, 함수 내부에서 매개변수의 프로퍼티를 직접 변경하면 함수 바깥의 원본 객체도 같은 메모리 주소를 가리키고 있기 때문에 변경이 그대로 반영됩니다. 이런 부수 효과(side effect)는 디버깅을 어렵게 만들기 때문에, React의 상태 업데이트처럼 불변성을 지켜야 하는 상황에서는 함수 내부에서 원본을 직접 수정하지 않고 스프레드 문법이나 배열의 map/filter 같은 순수 함수를 이용해 새로운 객체를 반환하는 패턴을 사용합니다. 반대로 의도적으로 원본 객체를 함수 내부에서 변경해 부수 효과를 활용하고 싶다면, 그 사실을 함수 이름이나 문서로 명확히 드러내어 호출하는 쪽에서 예상치 못한 변경에 놀라지 않도록 하는 것이 좋은 설계입니다. 이 질문은 순수 함수와 부수 효과, 그리고 불변성 유지 패턴에 대한 이해를 함께 보여줄 수 있는 좋은 기회입니다.
</details>
